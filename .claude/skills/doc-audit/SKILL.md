# ドキュメント間整合性チェック（doc-audit）

`docs/service-spec.md`（ビジネスルールの単一情報源）と、他の `docs/*.md` との間に矛盾・陳腐化がないかを検出する。`docs/adr/` 配下（不可逆な技術決定の記録）は対象外。

## 重要な前提: 「あるべき仕様」と「現在の実装を記述したドキュメント」を区別する

`docs/` 配下には性質の異なる2種類のドキュメントが混在している。矛盾を見つけた時、どちらの性質かによって取るべき対応が逆になるため、必ず区別すること。

- **仕様/意図ドキュメント**（`service-spec.md`、`glossary.md`、`user-stories.md` のうち未実装のストーリー 等）: これから作る・あるべき姿を記述する。矛盾が見つかったら `service-spec.md` の内容に合わせて修正してよい
- **実装記述ドキュメント**（`data-model.md`、`signup-flow.md`、`order-flow.md`、`operations-order.md`、`user-stories.md` のうち実装完了済みのストーリー 等）: 現在実際に動いているコード・DBを記述する。矛盾が見つかっても **安易に「仕様に合わせて書き換え」てはいけない**。実装が `service-spec.md` とまだ異なっているなら、それは実装記述としては正しい内容であり、「移行未完了」の注記を追加するだけに留める

判断を誤ると、実際にはまだ実装されていない仕様をさも実装済みであるかのようにドキュメントに書いてしまい、後でそれを読んだ AI・エンジニアが誤ったコードを書く原因になる。

**判断に迷ったら、関連する Linear issue の status を確認する**: `Done` なら実装記述（コード側が正）、`Backlog`/未着手なら仕様/意図（`service-spec.md` 側が正）として扱う。

## 手順

**Step 1: `service-spec.md` からキーとなるビジネスルールを洗い出す**

- ランク名・料金・仕入れ上限・退会条件・招待ルール等、数値や固有名詞を含む記述を抽出する

**Step 2: 対象ファイルを確認する**

```bash
ls docs/*.md
```

- `docs/adr/` 配下は対象外

**Step 3: 各ファイルを Step 1 の用語・数値で照合する**

```bash
grep -n "<キーワード>" docs/*.md
```

**Step 4: 矛盾を見つけたら、そのドキュメントの性質を判定する**

- 該当する機能の Linear issue（`mcp__linear__list_issues`, team: BRAND）を検索し、status を確認する
  - `Done` → 実装記述ドキュメントとして扱う（コードが正。書き換えず「移行未完了」の注記を追加する案を出す）
  - `Backlog`/未着手 → 仕様/意図ドキュメントとして扱う（`service-spec.md` に合わせて修正する案を出す）

**Step 5: レポートとして提示する**

- Linear と同様、ドキュメントへの書き込みも必ずユーザー承認後に行う
- レポートには「矛盾箇所」「性質判定（仕様 or 実装記述）」「提案する対応」を明記する
- 数値・固有名詞は書き写さず、可能な限り `service-spec.md` への参照に置き換えることを推奨する（シングルソーシング）

**Step 6: 矛盾がなければ「整合性OK」として終了する**

## 注意事項

- このスキルは `service-spec.md` の変更差分だけでなく、`docs/*.md` 全体の棚卸しにも使える
- コードの実装状況そのものを直接確認する必要がある場合（Linear issue の記載だけでは判断できない場合）は、該当コードを `Read`/`grep` して確認する
