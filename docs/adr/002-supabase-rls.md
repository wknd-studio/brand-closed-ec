# ADR-002: Supabase PostgreSQL + RLS でデータアクセスを制御する

## ステータス

Accepted

## コンテキスト

このサービスでは会員ランクによって閲覧できる商品・注文が異なる。アプリケーションコードだけでアクセス制御を実装すると、実装ミスやバグによってランク外の商品や他会員の注文が漏洩するリスクがある。データベースレベルで確実にアクセス制御する方法が必要だった。

## 決定

**Supabase PostgreSQL** をデータベースとして採用し、**Row Level Security（RLS）** でアクセス制御を実装する。

## 代替案

| 案                             | 却下理由                                                                    |
| ------------------------------ | --------------------------------------------------------------------------- |
| アプリコードのみでアクセス制御 | 実装ミス・バグによるデータ漏洩リスクが残る。DB レベルの保護がない           |
| Firebase Firestore             | PostgreSQL のリレーショナルモデルが使えない。RLS 相当の細かい制御が難しい   |
| Prisma + 素の PostgreSQL       | RLS のサポートが限定的。Supabase の管理コンソール・SDK の恩恵が受けられない |

## 結果

### メリット

- アプリコードにバグがあっても、DB レベルで不正アクセスをブロックできる
- ランクフィルタリング（商品の `min_rank` と会員の `rank` の比較）を RLS ポリシーとして定義できる
- Supabase の管理コンソールで DB・RLS・ログを一元管理できる
- `supabase-js` SDK が RLS を自動的に適用するため、クエリごとに条件を書き忘れるリスクがない

### 制約・注意点

- Supabase の JWT と Clerk の JWT を統合する必要がある（Clerk の JWT を Supabase に渡す設定が必要）
- RLS ポリシーはマイグレーションとして管理し、ローカル・stg・prod で常に同一の状態を保つ
- RLS が有効なテーブルへの書き込みには、別途 INSERT / UPDATE ポリシーが必要
