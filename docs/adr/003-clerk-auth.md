# ADR-003: 認証に Clerk を採用する

## ステータス

Accepted

## コンテキスト

会員の認証（登録・ログイン・セッション管理）を実装する方法を決定する必要があった。このサービスは招待制であり、招待コード検証後に会員登録フローに誘導する仕組みが必要。また、会員ランクをトークンに含めて Server Components や RLS から参照できる構造が求められた。

## 決定

認証基盤として **Clerk** を採用する。

## 代替案

| 案                  | 却下理由                                                                           |
| ------------------- | ---------------------------------------------------------------------------------- |
| Supabase Auth       | 機能はシンプルだが、publicMetadata・カスタム JWT クレームの柔軟性が Clerk より低い |
| Auth.js（NextAuth） | Edge Runtime でのセッション管理に制約がある。設定の複雑さに対してメリットが少ない  |
| 自前実装            | セキュリティリスクが高く、実装・運用コストが大きい                                 |

## 結果

### メリット

- メールアドレス・パスワード認証をすぐに利用できる
- `publicMetadata` に会員ランク（`rank`）を保存し、JWT クレームとして Supabase RLS から参照できる
- `@clerk/nextjs` の `middleware` で未認証ユーザーのルートガードが簡単に実装できる
- Clerk のホスト型ログインページで PCI / セキュリティ要件を満たしやすい

### 制約・注意点

- **ユーザー情報が Clerk と Supabase の2箇所に存在する**。Clerk が認証情報（メール・パスワード）を管理し、Supabase がランク・招待元等のビジネスデータを管理する
- ランクの変更は Clerk の `publicMetadata` と Supabase の `users.rank` の両方を更新する必要がある
- Supabase に渡す JWT は Clerk の JWT テンプレートを使って生成する
