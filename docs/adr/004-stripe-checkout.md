# ADR-004: 注文決済に Stripe Invoice を採用する

## ステータス

Accepted（旧タイトル「Stripe Hosted Checkout（SAQ A）を採用する」から変更）

## コンテキスト

会員が商品を注文する際の代金回収方法を決定する必要があった。このサービスは**無在庫転売型**であり、注文を受けた後に運営者が仕入れ先へ発注する。そのため、以下の制約がある。

1. **要相談商品の価格が注文時に未確定**: カートに入れた時点では価格がなく、運営者が仕入れ先と交渉した後に金額が確定する
2. **月次仕入れ上限チェックが請求書発行時にも必要**: 注文時の固定価格分と、請求書発行時の全額チェックの2段階でチェックする
3. **運営者が請求書を手動発行する運用**: 運営者が管理画面で金額を入力し、Stripe から会員へ請求書メールを送付する

これらの制約から、注文と同時に決済を完了させる即時決済モデルは採用できない。

## 決定

注文代金の回収に **Stripe Invoice** を採用する。カード情報の入力は Stripe が発行する請求書内のリンク先（stripe.com）で行うため、**SAQ A 準拠**を維持できる。

### 決済フロー

```
会員が注文 → 運営者が Stripe Invoice を作成・送付
→ 会員が請求書メール内のリンクをクリック（stripe.com へ遷移）
→ Stripe のページでカード入力・決済
→ invoice.paid Webhook でシステムが注文ステータスを「入金確認済み」に更新
```

### SAQ A 準拠について

SAQ A の要件は「カード番号の入力が自社サーバーを経由しないこと」である。Stripe Invoice の支払いリンクは stripe.com にホストされたページに遷移するため、Stripe Hosted Checkout と同様に SAQ A 準拠となる。

## 代替案

| 案                                 | 却下理由                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------------- |
| Stripe Hosted Checkout（即時決済） | 要相談商品の価格が注文時に未確定なため、注文と同時に決済できない                        |
| Stripe Elements（カスタム UI）     | SAQ A-EP 準拠が必要になりセキュリティ要件が増える。また即時決済モデルになるため採用不可 |
| 他の決済プロバイダ（PayPay 等）    | Stripe Subscription（会員ランク課金）との統合が前提のため、一本化を優先                 |
| 自前決済実装                       | PCI DSS 完全準拠が必要となり、現実的でない                                              |

## 結果

### メリット

- 注文時に価格が未確定の要相談商品を含む注文でも、請求書発行のタイミングで金額を確定できる
- 月次仕入れ上限チェックを請求書発行時に実施できる（注文後にプランダウングレードした場合も注文時点の上限を基準にチェック可能）
- カード情報が自社サーバーを経由しないため、**PCI DSS SAQ A** に準拠できる
- Stripe が請求書 UI・メール送付・支払いページを担当するため、実装工数が削減される
- `invoice.paid` Webhook で入金確認を自動化できる

### 制約・注意点

- 会員ランクの月額費用は Stripe Subscription で管理する（ADR-007 参照）。Invoice は注文代金のみに使用する
- Webhook の受信エンドポイントは署名検証を必ず実装する
- Invoice 作成 API の呼び出しは Server Action で行い、Stripe の秘密鍵をクライアントに渡さない
- 入金後のキャンセル時は Stripe Refund が必要。返金ポリシーは原則返金なし、例外対応は運営者判断（システム外処理）
