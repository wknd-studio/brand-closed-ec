# ADR-006: 招待制アーキテクチャを採用する

## ステータス

Accepted

## コンテキスト

このサービスはブランドの卸売商品を特定の会員のみに提供するクローズド EC である。不特定多数が登録・閲覧できる状態はサービスの性質と相容れない。招待を受けた人だけが利用でき、未認証ユーザーには商品情報等を一切見せない仕組みが必要だった。

## 決定

**招待コードを持つユーザーのみが登録できる**アーキテクチャを採用する。

公開ページは以下の2つのみ：

| ページ            | 説明                 |
| ----------------- | -------------------- |
| `/invite`         | 招待コード入力ページ |
| `/login`（Clerk） | ログインページ       |

上記以外のページは未認証ユーザーに対して **404 を返す**。  
ログアウト後は `/login` へリダイレクトする。

## 代替案

| 案                                                | 却下理由                                                                                                 |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| ログインページも含め全ページを非公開（404）にする | ログアウト後の遷移先がなく UX が不自然。会員情報が露出するわけでもないためログインページは公開で問題ない |
| 管理者承認制の登録フォームを公開する              | 登録希望者が殺到する可能性があり、運営コストが増える                                                     |
| IP アドレス制限                                   | 会員の利用環境が固定できないため現実的でない                                                             |

## 結果

### メリット

- 商品情報・会員情報・価格は未認証ユーザーに一切公開されない
- ログインページを公開することで、会員がログアウト後に自然に戻れる
- 招待ルートが `/invite` のみに集約されており、新規登録の入口が明確
- `robots.txt` + `X-Robots-Tag: noindex` で検索エンジンからのインデックスを防ぐ

### 制約・注意点

- 未認証アクセスを 404 にする処理は `middleware.ts`（Cloudflare Workers）で実装する
- `/invite` と `/login` は middleware の除外リストに含める
- `/invite` は公開するため、招待コードの検証はサーバーサイドで必ず行う
- 招待コードには有効期限・最大使用回数を設けて使い回しを防ぐ
