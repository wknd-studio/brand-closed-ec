# 完了の定義（Definition of Done）

「完了」とは何かを定義する。ユーザーストーリーの実装・バグ修正が「完了」と見なされるための基準。
顧客・開発者が同じ基準を共有することで、手戻りを防ぐ。

---

## フィーチャー（ユーザーストーリー）の完了基準

以下をすべて満たしたとき、ユーザーストーリーは「完了」とする。

### 1. 受け入れ条件を満たしている

- `user-stories.md` に記載された受け入れ条件（【ユーザーが確認できること】【システムが保証すること】）をすべて満たしている
- ステージング環境で実際に操作して確認済み

### 2. コード品質

- `task check`（typecheck → lint → ユニットテスト → 統合テスト）が green である（push・PR 作成前に実行する）
- `pnpm format`（Prettier）を適用済み

### 3. テスト

- CLAUDE.md の「テスト自動選択ルール」に従い、実装内容に応じたテスト（ユニット・統合）が追加されている
- CLAUDE.md の「変更した層ごとの確認ルール」に従い、触った層ごとに対応する確認を行っている（上位の層だけテストして終わらせない）
- E2E テスト（Playwright）の新規追加は、複数画面をまたぐクリティカルな業務フローに限り最小限とする。既存フローに影響する変更では、該当する spec を実行して通過を確認する

### 4. セキュリティ・アクセス制御

実装内容に応じて以下を確認する。

| 確認項目                                                 | 確認方法                                                                                                         |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| RLS が正しく設定されている                               | 別の会員アカウントでログインし、他会員のデータ（注文・住所・カート等）にアクセスできないことをステージングで確認 |
| 未認証ユーザーは `/invite` と `/login` 以外に 404 が返る | 未ログイン状態で直接 URL アクセスして確認                                                                        |
| ランク制限商品は対象外ランクに表示されない               | 対象外ランクのアカウントで商品一覧・詳細 URL にアクセスして確認                                                  |
| Stripe Webhook エンドポイントが署名検証を実装している    | 統合テストで確認し、`high-risk` PR として人間が差分を精読する                                                    |
| 管理者・運営者機能が会員ロールからアクセスできない       | 会員アカウントで管理画面 URL に直接アクセスして確認                                                              |

### 5. PR レビュー

- PR が `develop` 向けに作成されている
- PR 説明にストーリー ID（例: `BRAND-XX`）・変更内容・実施したテスト（証拠）が記載されている
- `high-risk` ラベルの PR は、人間が差分を精読してからマージする
- それ以外の PR は、CI の結果と PR 説明の証拠欄（実施したテスト等）で判断する（承認は必須としない）

### 6. CI が全グリーン

- GitHub Actions の全チェックが通過している

### 7. GitHub issue の更新

- 対応する GitHub issue がクローズされている（PR 説明に `Closes #<issue番号>` を書き、マージ時に自動でクローズする）

---

## バグ修正の完了基準

1. 再現手順が PR 説明に記載されている
2. 修正後に同じ手順で再現しないことをステージングで確認済み
3. 同種のバグを防ぐためのテストが追加されている（追加が困難な場合は理由を明記）。レビューをすり抜けたバグの場合は、該当パスを `.github/labeler.yml` に加えるか、同じバグを検出する lint・テストに変換する
4. 上記「コード品質」「CI が全グリーン」「PR レビュー」を満たしている

---

## ステージング確認の原則

- **動くソフトウェアでの確認が最優先**。コードレビューのみで「完了」としない
- 運営者側の操作（注文ステータス更新・請求書発行等）は管理者アカウントで確認する
- 会員側の操作は複数のランク（少なくとも最低ランクと上位ランクの1つ）で確認する

---

## 完了の定義に含まれないもの

- 本番環境へのデプロイ（デプロイは別途リリース判断）
- パフォーマンス最適化（別途タスクとして扱う）
- `collaboration.md`・`definition-of-done.md` 等のドキュメント更新（コードに影響しない変更）
