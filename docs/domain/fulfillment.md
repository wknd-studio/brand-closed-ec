# 配送・分割出荷（Fulfillment）

## このコンテキストの責務

このドキュメントは「[[procurement]]で発注・入荷（または仕入れ先直送の発注）が済んだ商品明細を、どう箱詰めして顧客に届けるか」を定義する。

**扱うこと**:

- 出荷（`shipments`）による、注文の一部または全部の梱包・発送・配達完了までの状態管理
- 1つの注文が複数の出荷に分かれる「分割出荷」の考え方
- 商品の配送ルート（事務所経由／仕入れ先直送）を表す拠点マスタ（`locations`）
- 出荷がいつ作成できるか（[[procurement]]側のどの状態を経由すれば作成可能になるか）の分岐条件

**扱わないこと**:

- 商品ごとの発注そのもの・入荷検品（`procurement_tasks`）は[[procurement]]が扱う。本ドキュメントが起点にするのは、`procurement_tasks.received_at`（事務所経由）または`ordered_at`（仕入れ先直送）が入った**後**の話であり、そこに至るまでの発注業務には立ち入らない
- 顧客からみた注文そのものの状態遷移（承認・支払い・キャンセル、`orders.status`）は[[ordering]]が扱う。`orders.status`は`paid`から先に進まず、`paid`以降の商品ごとの進捗は本ドキュメントと[[procurement]]から都度算出する
- 配達後に判明した不良品・誤配送に対する返品・返金対応は[[returns]]が扱う。本ドキュメントは`delivered`（配達完了）までで終わる
- 配送業者との契約・送料計算・配送伝票発行システムそのものの選定は業務ドメインの範囲外（現状は手作業で配送業者に引き渡す運用。「参考資料」の`archive/operations-order.md`参照）
- 「運営スタッフが出荷操作を行ってよいか」という権限の定義そのものは[[admin-rbac]]が扱う。本ドキュメントは権限マトリクスの結果として何が起きるか（業務ルール）のみを扱う

## 主要な概念・用語

`docs/glossary.md`には現時点で配送・出荷まわりの用語が存在しないため、以下はすべて新規定義であり`glossary.md`側への追記が必要。

| 用語                                       | 定義                                                                                                                                                                             |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **出荷**                                   | 実際に顧客へ発送する1箱の単位。DB上は`shipments`の1行。1つの注文（`orders`）に対して出荷は複数存在しうる                                                                         |
| **分割出荷**                               | 1つの注文に含まれる商品が、事務所への入荷タイミング・仕入れ先直送の発注タイミングの違いにより、複数回に分けて発送されること。揃った商品から先に出荷を作成できる                  |
| **発送拠点（`locations`）**                | 商品がどこから顧客へ発送されるかを表す参照マスタ。初期投入データは`'office'`（事務所）と`'supplier_direct'`（仕入れ先直送）の2行を想定する                                       |
| **受領必須フラグ（`requires_receiving`）** | 発送拠点ごとに、出荷作成前に事務所での受領（[[procurement]]の`received_at`）を必須とするかどうかを表すデータ。`'office'`は`true`、`'supplier_direct'`は`false`                   |
| **出荷元拠点（`origin_location_code`）**   | ある出荷が実際にどの拠点から発送されたかを`shipments`側に記録する列。`order_items.fulfillment_location_code`から辿れば分かる情報だが、出荷単体で判断できるようにするための冗長化 |
| **出荷ステータス**                         | `preparing`（梱包準備中）→`shipped`（発送済み）→`delivered`（配達完了）の3値。注文単位ではなく出荷（箱）単位で進む                                                               |

## 業務ルール・不変条件

### 確定しているもの

- **「注文」と「出荷」は別エンティティ**: 同じ注文内でも商品ごとに一次卸業者・入荷タイミングが異なるため、注文＝1回の発送という前提を置くと、一番入荷が遅い商品に発送全体が引きずられる。そこで`orders`（顧客が申し込んだ内容）と`shipments`（実際に発送する箱）を分離し、揃った商品から先に発送できるようにする
- **出荷は事後に作成する箱の単位**: `shipments`は顧客が指定する概念ではなく、運営スタッフが「揃った`order_items`」を選んで作成する。1回の注文に対して`shipments`が1件とは限らない
- **出荷作成の分岐条件は発送拠点で決まる**（[[procurement]]の業務ルールと対）:
  - `requires_receiving = true`（事務所経由・`'office'`）: [[procurement]]の`procurement_tasks.received_at`が入り、商品が事務所に届いてから出荷を作成できる
  - `requires_receiving = false`（仕入れ先直送・`'supplier_direct'`）: `received_at`を経由せず、[[procurement]]の`procurement_tasks.ordered_at`（仕入れ先へ発注した時点）が入った段階で出荷を作成できる。この場合、発注時に顧客の配送先住所（`orders.shipping_address_snapshot`）を仕入れ先へ伝える必要があるが、これは運営スタッフの業務フローであり、既存の`orders`の列で足りるためスキーマ上の追加は不要
- **1つの出荷は同じ発送拠点の商品のみで構成される**: 1つの`shipments`に含まれる`order_items`は、全て同じ`fulfillment_location_code`でなければならない（物理的に1箱が事務所発送と仕入れ先直送を同時に兼ねることはありえないため）。この制約はDBのCHECK制約ではなくアプリケーション層で検証する
- **1明細は同時に1つの出荷にしか属さない**: `order_items.shipment_id`は単一FK（NULL可）。数量単位でさらに分割して送る（例: 10個のうち3個だけ先に送る）ケースは当面想定しない。まだ発送されていない明細は`shipment_id IS NULL`のまま「未発送」として一覧できる（[[procurement]]の`procurement_task_id IS NULL`＝対応待ちキューと同じパターン）
- **出荷の進捗は都度算出、キャッシュしない**: `orders.status`は`paid`から先に進まない。ある注文が「一部発送済み」なのか「全て配達完了」なのかは、`orders`に紐づく`shipments`/`order_items`をJOINして都度計算する（[[procurement]]の集計値と同じ考え方）。画面表示が重くなった場合のみ、後から同期用のキャッシュ列を追加できる
- **RLS・書き込み経路**: 顧客は自分（または所属組織）の注文に紐づく出荷を`shipments`テーブルからSELECTのみ可能（追跡番号・配送状況の確認用途）。書き込みは[[procurement]]と同様に管理画面API（service role経由）に一本化し、顧客向けINSERT/UPDATE/DELETEポリシーは設けない。`order_items.shipment_id`の更新も同じAPI経由に統一する。一方`locations`（発送拠点マスタ）は運営内部の情報であり、顧客向けSELECTポリシーは設けず参照・書き込みともに管理画面APIに一本化する
- **`locations`はカタログ表示に使わない参照テーブル**: `member_ranks`と似た「行データとして持つことで将来の拠点追加をマイグレーション無しのINSERTだけで対応できるようにする」設計だが、`member_ranks`と異なり顧客向けには公開しない
- **`locations`と`addresses`は別物**: `addresses`は顧客が指定する配送「先」、`locations`は商品が出発する配送「元」であり、役割が逆になる。`addresses.user_id`がNOT NULLである以上、人でも組織でもない`locations`を同じテーブルに混ぜるとポリモーフィックな関連になってしまうため統合しない
- **旧オペレーションフローとの対応**: `archive/operations-order.md`（凍結済み）では`orders.status`が単一の値で`preparing`（発送準備中）→`shipping`（配送中）→`delivered`（配送完了）と遷移し、調達担当が管理画面のボタンで遷移させる運用だった。新設計ではこれらの値は`orders.status`から廃止され、出荷単位の状態（`preparing`/`shipped`/`delivered`）として`shipments`側に移った。**配送伝票の作成・追跡番号の取得・配送業者への引き渡しという運営スタッフの作業内容自体は変わらない**（引き続き人手で行う）

### まだ決まっていない・要確認事項

- 🔲 **発送通知・配達完了通知メールの実装**: `archive/operations-order.md`時点では未実装（BRAND-69で対応予定）で、会員への連絡は手動運用だった。新設計の`shipments.shipped_at`/`delivered_at`を起点にした自動送信に置き換えるかは実装時の検討事項
- 🔲 **数量単位での出荷分割**: 1つの明細（同じ商品・同じ数量のまとまり）をさらに複数の出荷に分割する（例: 10個のうち3個だけ先に送る）運用は現時点で対象外。必要になった場合は`shipment_items`（`shipment_id`, `order_item_id`, `quantity`）という中間テーブルへ拡張できる余地は設計上残されている
- 🔲 **`paid`以降のキャンセル・出荷済み以降の返品との境界**: `shipping`（＝`shipments.status='shipped'`）以降のキャンセルは配達を止めることが困難なため原則対応不可という旧運用があったが、新設計での正式な業務ルールとしての明文化、および[[returns]]との境界の切り分けは未確定
- 🔲 **配送SLA・配送業者選定基準**: 配送業者との契約形態・複数業者の使い分け基準は本ドキュメントの対象外資料に記載がなく、運営スタッフの裁量による現行運用がそのまま続くのか、将来ルール化するのかは未確認
- 🔲 **`shipments`作成のUI・操作フロー詳細**: 「揃った`order_items`を選んで出荷を作成する」という業務ルールは確定しているが、管理画面上の具体的な操作手順（一括選択のUI等）は未設計

## 他コンテキストとの関係

- [[procurement]]: 出荷を作成できるようになる起点（`received_at`または`ordered_at`）は[[procurement]]が管理する。`fulfillment_location_code`／`locations.requires_receiving`という区分の値の定義は本ドキュメントの責務だが、その値によって発注タスクの運用がどう分岐するかは[[procurement]]側の記述を正とする
- [[ordering]]: `orders.status`は`paid`から先に進まないため、`paid`以降の配送進捗は`orders`側の列ではなく本ドキュメントの`shipments`から都度算出する。`order_items.fulfillment_location_code`（注文確定時点のスナップショット）は[[ordering]]が作るが、その値の意味（事務所経由／仕入れ先直送の区分そのもの）の定義は本ドキュメントの責務
- [[admin-rbac]]: 「調達担当」ロールが出荷の作成・追跡番号の入力・配達完了記録を実行できるかの権限マトリクスの正は[[admin-rbac]]にある。本ドキュメントはその権限が実際の業務でどう使われるかを定義する
- [[returns]]: 配達完了後に判明した不良品・誤配送の返品・返金対応は[[returns]]が扱う。本ドキュメントは`delivered`に達するところまでで、その後の返品申請フローには立ち入らない。発送後の返品における返送先・受領方法は本ドキュメント執筆時点で未設計であり、[[returns]]側の「まだ決まっていない・要確認事項」にも同じ論点が記載されている
