# 会員登録（招待制）・個人/法人・退会

## このコンテキストの責務

このドキュメントは「誰が会員になれるか・どうやって会員になるか・会員資格がどう終わるか」を定義する。

**扱うこと**:

- Waitlist（参加希望送信・管理者承認）を起点とした会員登録フロー
- 個人会員（`users`）と法人会員（`organizations`/`organization_memberships`）の区別と、両者が排他的である理由
- 招待の仕組み（会員間の招待・招待記録）
- アカウント停止・強制退会・退会・再入会のルール
- Clerkとの役割分担（本人確認・認証の正はどちらか）

**扱わないこと**:

- ランク・サブスクリプション・初期費用・プラン変更そのもののルール（`subscribed_at`起点の月次上限計算やStripe連携の詳細）は[[subscription-billing]]（未着手）が扱う。本ドキュメントは「会員資格を持っているか／持っていないか」までを扱い、「どのランクか」は扱わない
- 運営スタッフ（管理者・請求顧客担当・調達担当）のロール・権限は`admin-rbac.md`（未着手、`db-schema-redesign.md`策定時点では`admin_users`/`admin_memberships`として設計済み）が扱う。本ドキュメントで「管理者」と書く場合も、あくまで会員側の業務ルールに対する運営者の関わり（強制退会の実行者等）として登場するだけで、権限マトリクスの正はそちらにある
- 法人会員内の注文承認権限（`org:admin`のみ承認可）は[[ordering]]（未着手）が扱う。本ドキュメントは`organization_memberships`が「誰がどの組織に所属しているか」を表す集約としての側面のみを扱う

## 主要な概念・用語

`docs/glossary.md`の「会員・ランク」「招待」セクションと整合させる。以下は本ドキュメントで新たに補足する用語（`glossary.md`側への追記が必要）。

| 用語                                                         | 定義                                                                                                                                                                                    |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Waitlist**                                                 | Clerkの`Waitlist` signup mode。ユーザーが`/waitlist`でメールアドレスを送信すると`pending`状態の`waitlistEntry`が作成され、管理者の承認（`invite()`）で招待メールが送られる              |
| **個人会員**                                                 | Clerkの個人User。DB上は`users`テーブルの1行に対応する。会員自身がランク・月次上限を持つ                                                                                                 |
| **法人会員（組織）**                                         | ClerkのOrganization。DB上は`organizations`テーブルの1行に対応する。ランク・月次上限は組織単位で共有される（`organization_memberships`で紐づく一般担当者は個人としてのランクを持たない） |
| **アカウント種別選択**                                       | サインアップ直後に個人/法人のどちらとして利用するかを選ぶオンボーディングステップ（`/onboarding/account-type`）。一度選ぶと動的な切り替えはない                                         |
| **代表者**                                                   | 法人登録時に組織を作成したユーザー。Clerk上`org:admin`として登録され、`users`側にも代表者本人の氏名・電話番号が反映される                                                               |
| **一般担当者**                                               | 法人組織に後から招待され所属するユーザー。個人としての会員ランク・月次上限を持たず、組織のランク・月次上限を共有する                                                                    |
| **停止**                                                     | 管理者がアクセスをブロックし課金を一時停止する、可逆的な操作。強制退会とは異なり関係は継続する                                                                                          |
| **強制退会**                                                 | 管理者権限で会員を退会させる、不可逆な操作。会員自身の退会ブロック条件（後述）を迂回できる                                                                                              |
| **初期費用支払い済みランク（`initial_fee_paid_rank_code`）** | 退会・再入会をまたいでも保持される「支払い済み最高ランク」のキャッシュ。再入会時・アップグレード時の初期費用二重課金判定に使う。詳細な金額計算は[[subscription-billing]]が扱う          |

## 業務ルール・不変条件

### 確定しているもの

#### 会員登録

- **登録には招待が必須**。招待なしでは登録できない（`archive/service-spec.md`「共通ルール」）。
- **アクセス制限の方式はWaitlist**: ユーザーが`/waitlist`で参加希望を送信し、管理者が`/admin/waitlist`で承認した人のみ`/sign-up`以降のフローに進める。旧「管理者がメールアドレスを直接指定して招待する」方式（Restricted signup mode + `/admin/invitations`）は廃止済み（`docs/waitlist-migration-plan.md`、PR #144）。
- **利用規約・プライバシーポリシーへの同意はClerk標準機能**（`compliance.legal_consent`）で必須化する。独自の同意ページは持たない。
- **個人/法人は排他**: 1ユーザーが個人会員としての会員ランクと法人組織メンバーとしての所属を両方持つことはない。判定は`organization_memberships`に自分のレコードが1件でもあるかで行い、動的な切り替えは発生しない（`specs/005-b2b-organization` FR-022）。
- **決済は個人・法人で共通**: どちらもStripe Checkoutで初期費用・月額費用を決済し、確定はStripe Webhook（`checkout.session.completed`）による非同期処理で行う（決済・ランクの詳細は[[subscription-billing]]）。
- **氏名・電話番号は各オンボーディング画面内で収集する**: 個人は`/onboarding/plan`、法人代表者は`/onboarding/organization`。汎用のプロフィール入力ゲート画面は意図的に作らない（`docs/signup-flow.md`設計決定事項#10）。
- **Webhookとサーバーアクションの二重upsert**: Clerkの`user.created`Webhookはベストエフォート配信のため、`selectPlan`・`createOrganization`側でも`users`が存在しなければ作成することで整合性を保証する。

#### 招待（会員間）

- **管理者は常に招待を発行できる**。会員は招待権限が付与されている場合に限り発行できる。招待権限の付与・剥奪は管理者が行う（`archive/service-spec.md`「招待システム」）。
- 会員ごとに招待上限数・使用済み招待数を管理する。管理者は上限数を自由に設定できる。招待には有効期限を設定できる。
- 誰が誰を招待したかをDBに記録する（`invited_by_user_id`）。将来のアフィリエイト特典計算に使用する想定だが、特典内容自体は未定（後述）。

#### アカウント停止・強制退会

- 管理者は任意の判断で**停止**（可逆・アクセスブロック＋課金一時停止）と**強制退会**（不可逆）を実行できる。
- 停止中: ログイン・サービス利用をブロックし、Stripeサブスクリプションを一時停止する（停止期間中の請求は発生しない）。進行中の注文は継続処理し、新規注文はブロックする。
- 停止解除: アクセスが即時復活し、Stripeの課金は次の請求期間から再開する（停止期間分は請求しない）。月間仕入れ上限は停止前の使用済み額を引き継ぐ。
- 強制退会: `paid`以降の注文がある場合でも管理者は実行できる（会員自身の退会チェックを迂回する）。管理画面に「入金済みで処理中の注文が N 件あります」という確認ステップを表示する。`paid`以降の注文はそのまま完走させ、運営側が手動で完了・キャンセルまで処理する。アカウント処理（ログインブロック・Stripe解約・論理削除）は即時実行する。

#### 退会・再入会

- 入会日から**6ヶ月間は退会できない**（最低利用期間）。
- `paid`以降（`paid`/`sourcing`/`ordered`/`preparing`/`shipping`）の注文が1件でもある場合、会員自身による退会をブロックする。`paid`より前のステータスはブロックしない（注文ステータスの詳細は[[ordering]]）。
- 退会後もデータは保持する（論理削除、`users.deleted_at`/`organizations.deleted_at`）。退会と同時にStripeサブスクリプションを解約する。
- 再入会時: 注文履歴・住所などのデータは論理削除のため引き継がれる。プランは再入会時に改めて選択する。初期費用は`initial_fee_paid_rank_code`を基準に、選択プランがそれ以下なら免除、上回れば差分を請求する（差分計算のルールは[[subscription-billing]]）。

#### データモデル（`db-schema-redesign.md`より）

- `users.clerk_user_id`と`organizations.clerk_org_id`はいずれも`WHERE deleted_at IS NULL`の**部分UNIQUE**にする。退会（論理削除）後に同じClerkアカウント・同じ組織で再登録すると、通常のUNIQUEでは一意制約違反になるため。
- `users`/`organizations`とも`rank_code`をNOT NULL・非正規化キャッシュとして持つ。更新は必ず`rank_changes`へのINSERTと同一トランザクションで行う（詳細は[[subscription-billing]]）。
- `organizations`の住所カラム（`postal_code`等）は廃止され、`addresses`（`type='headquarters'`）に統合されている。組織の本店所在地は`addresses`テーブル側で1組織1件の部分UNIQUEインデックスで保証する。
- `organization_memberships.clerk_role`はCHECK制約を持たない意図的な設計（詳細な理由は`admin-rbac.md`「ロールのバリデーションについて」と同じトレードオフ）。認可判定はアプリケーション層の`has({ permission })`が担う。

### まだ決まっていない・要確認事項

- 🔲 **アフィリエイト特典の内容**: 招待した会員・招待された会員それぞれへの特典内容は未定。「誰が誰を招待したか」の記録（`invited_by_user_id`）は実装済みのため、特典ロジックは後から追加可能（`archive/service-spec.md`）。
- 🔲 **付加機能（専任担当者サポート・優先対応・専用ライン・月次仕入れレポート・カスタムレポート）のランク別提供**: `glossary.md`に旧5ランクモデル時代の記述が残っているが、現行`service-spec.md`にはランクごとの付加機能の記載が無く、新7ランクモデルでどのランクに何が付くか（あるいは廃止されたか）が未確定。`SLA対応`（ENTERPRISE）のみ現行仕様でも有効と確認済み。
- 🔲 **既存会員への氏名・電話番号の遡及対応**: 本番未リリースのため対象ユーザーがおらず、本リリースのスコープ外とされている（`specs/005-b2b-organization/spec.md` FR-020）。`users.profile_completed_at`は将来の遡及対応判定用に予約されているカラムだが、実装は未着手。
- 🔲 **Waitlist招待メールのリンク遷移**: `waitlistEntries.invite()`は`createInvitation()`と異なり`redirectUrl`を指定できないため、招待リンクは必ずClerkホスト型ページ（Account Portal）を経由する。この制約によるE2Eテストのカバレッジ縮小（`docs/signup-flow.md`設計決定事項#13）は許容されているが、恒久対応（自社ドメインでのホスト型ページ運用等）は検討されていない。

## 他コンテキストとの関係

- [[subscription-billing]]（未着手）: ランク・サブスクリプション・初期費用・プラン変更そのもののルールを扱う。本ドキュメントは「ランクを持つ主体（個人/法人）がどう成立し、どう終わるか」までを扱い、ランクの値そのもの・料金・月次上限計算は完全にそちらへ委ねる。`rank_code`/`initial_fee_paid_rank_code`はどちらのドキュメントにも登場するキャッシュ列であり定義が重複しないよう注意する。
- [[ordering]]（未着手）: 退会ブロック条件（`paid`以降の注文有無）・強制退会時の未完了注文の扱いは、注文ステータスの定義そのものに依存する。注文ステータスの遷移・詳細は[[ordering]]側の責務。法人組織内の注文承認権限（`org:admin`のみ）も[[ordering]]が扱う。
- `admin-rbac.md`（未着手）: アカウント停止・強制退会・招待コード発行/無効化はいずれも運営者（管理者ロール）のみが実行できる操作。実行可否の権限マトリクスの正は`admin-rbac.md`にあり、本ドキュメントはその実行結果として何が起きるか（業務ルール）のみを定義する。
- `catalog.md`（未着手）: 商品のランク制限（最低閲覧ランクを下回る会員は閲覧・購入不可）は、会員が「ランクを持つ」ことを前提にした判定であり、判定ロジック自体は`catalog.md`側が扱う。
