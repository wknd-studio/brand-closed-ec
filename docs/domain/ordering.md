# カート・注文・Checkout/Invoice・法人承認（Ordering）

## このコンテキストの責務

このドキュメントは「会員がカートに商品を入れてから、注文が`paid`（入金確認済み）に達するまで、注文というものがどう成立し、どう状態遷移するか」を定義する。

**扱うこと**:

- カート（`cart_items`）に商品を入れる〜注文確定（`place-order`）までの一連の操作
- 商品属性（`payment_timing`）による、明細の支払いタイミング分類（`at_order`/`after_order`）の根拠。**要相談商品（`is_negotiable`）はVer1では扱わない（2026-09-14、[[catalog]]参照）ため、Ver1では全明細の価格が注文確定時点で確定している**
- 注文確定時の住所スナップショット化（新規入力／登録済み住所の選択、個人の住所帳／組織の共有住所帳）
- 注文ステータス（`orders.status`）の`cancelled`（決済単位作成前のキャンセル）
- 注文明細（`order_items`）への商品情報スナップショット化（商品名・単価・ブランド・発注拠点）
- ステータス変更の追記専用ログ（`order_status_changes`）とメール通知

**扱わないこと**:

- **決済フローの自動分岐（Checkout／Invoice）、決済単位ごとの状態遷移（`pending_payment`〜`paid`）、月次仕入れ上限チェックの実行タイミングは2026-09-13以降[[settlement]]が扱う**。本ドキュメントは「支払いタイミングで明細を`at_order`/`after_order`に分類するところまで」で終わり、その分類がどう決済単位（`order_settlements`）に落とし込まれるかは[[settlement]]の責務（下記「チェックアウト分割」の用語定義・業務ルールは旧設計の記録として残すが、[[settlement]]側の設計が正）
- `paid`到達**後**の商品明細ごとの発注・入荷の進捗は[[procurement]]が扱う。「`paid`」は本ドキュメントでは`orders.status`の値ではなく、各決済単位（`order_settlements.status`）が取る値になった点に注意（[[settlement]]参照）
- 梱包・分割出荷・配送状況（`shipments`）は`fulfillment.md`（未着手）が扱う
- 発注済み商品の返品・返金は`returns.md`（未着手）が扱う
- 会員ランクの定義・序列・月次仕入れ上限の金額そのものは[[subscription-billing]]が扱う。本ドキュメントはランク・上限額を「注文確定時点の値としてスナップショットする」ところまでを扱い、値そのものの計算根拠には立ち入らない
- 商品情報（価格・在庫状況・要相談商品かどうか・支払いタイミング属性の設定）そのものの管理は[[catalog]]が扱う。本ドキュメントはカートに入った後の商品情報をスナップショットとして扱うのみ
- 法人組織の作成・メンバー招待・`org:admin`/`org:member`ロールが何者かという定義そのものは[[membership]]が扱う
- 運営スタッフ（管理者・請求顧客担当・調達担当）が何を実行できるかの権限マトリクスは`admin-rbac.md`が扱う
- **法人組織内の注文承認フロー（2026-09-13廃止）**: 本格的な法人組織対応（1組織に複数メンバー、担当者の発注を管理者が承認する運用）はVer1では実装しないと決定したため、「一般担当者が発注→承認待ち→管理者が承認/却下」という機能自体が不要になった。Ver1では法人会員も個人会員も同じ注文フロー（本ドキュメントの内容）をそのまま使う。関連して`orders.status`の`pending_approval`/`auto_approved`/`rejected`という値、`orders.requested_by_user_id`/`approved_by_user_id`列は不要（将来、複数メンバー対応の法人組織機能を再構築する際に、承認フローとして再設計する）

## 主要な概念・用語

`docs/glossary.md`の「カート・注文・決済」節は現行実装と乖離した旧5ランクモデル時代の記述だったため、本ドキュメント執筆に合わせて更新する（後述）。

| 用語                                                             | 定義                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **カート**                                                       | 購入前に商品を一時的に保存する場所。DB上は`cart_items`（`user_id`, `sanity_product_id`, `quantity`）。注文確定前は何度でも自由に変更でき、スナップショット化されない                                                                                                                                                                                                                                                                                          |
| **Checkoutフロー**                                               | カート内の全商品が注文時払い（`payment_timing='at_order'`）の場合に採用される決済フロー。Stripe Checkoutで即時決済し、運営者の決済作業はゼロ                                                                                                                                                                                                                                                                                                                  |
| **Invoiceフロー**                                                | カートに注文後払い（`payment_timing='after_order'`）の商品が1つでも含まれる場合に採用される決済フロー。運営者が内容確認後にStripe Invoiceを手動発行する                                                                                                                                                                                                                                                                                                       |
| **チェックアウト分割（2026-09-13廃止・[[settlement]]参照）**     | ~~カートに注文時払い商品と注文後払い商品が混在する場合、1回のチェックアウト操作から2件の`orders`（`checkout`用・`invoice`用）を自動生成すること。同一チェックアウト由来であることは`split_group_id`で関連付ける~~ 旧設計。`shipments.order_id`が単一`orders`しか参照できず分割後の2件をまたいだ同梱ができないという欠陥が発覚したため廃止。現在は`orders`を常に1行のまま保ち、代わりに明細単位の決済単位（`order_settlements`）に振り分ける（[[settlement]]） |
| **注文（Order）**                                                | カートの内容を確定して決済手続きを開始した記録。DB上は`orders`の1行。個人・法人、Checkout・Invoiceいずれのフローも同じテーブル・同じ`status`遷移で扱う                                                                                                                                                                                                                                                                                                        |
| **注文明細（OrderItem）**                                        | 注文に含まれる商品ごとの内訳。DB上は`order_items`。商品名・単価・ブランド・発注拠点を注文確定時点の値としてスナップショットする（[[catalog]]の商品データとは別に保持）                                                                                                                                                                                                                                                                                        |
| **住所スナップショット**                                         | 注文確定時点の配送先・請求先住所を`orders.shipping_address_snapshot`/`billing_address_snapshot`（JSONB）に複製したもの。以後`addresses`側の住所が変更・削除されても注文の記録は変わらない                                                                                                                                                                                                                                                                     |
| **月次仕入れ上限チェック**                                       | 決済単位（`order_settlements`）の作成時に行う、月間仕入れ上限との突合。個人会員はユーザー単位、法人会員は組織単位で判定する（[[subscription-billing]]、実行タイミングの詳細は[[settlement]]）                                                                                                                                                                                                                                                                 |
| **発注期限（`procurement_due_at`、2026-09-13: V1では作らない）** | ~~注文に含まれる商品を配送SLAに間に合わせるためにいつまでに一次卸業者へ発注すべきかの期限~~ 顧客への配送日数のお約束（SLA）自体が現状存在しないため、この列・自動計算ロジックはV1では作らない（[[procurement]]参照）。対応待ちキューは単純に「対応待ちになった順」で並べる                                                                                                                                                                                    |

## 業務ルール・不変条件

### 確定しているもの

**明細の支払いタイミング分類（2026-09-13改訂: 決済フローの分岐そのものは[[settlement]]へ移管）**

- 明細の支払いタイミング（`at_order`/`after_order`）はカート内商品の`payment_timing`（[[catalog]]で定義）で自動判定する。**要相談商品（`is_negotiable=true`）はVer1では扱わない（2026-09-14、[[catalog]]参照）ため、Ver1では全明細の価格が確定している前提で分類できる**
- カートが単一の支払いタイミングのみで構成される場合でも混在する場合でも、`orders`は常に1件のみ作成される（旧設計の「2件の`orders`に分割する」`split_group_id`は廃止済み。経緯・新設計は[[settlement]]参照）
- 分類判定は、会員が閲覧・操作できる情報（カート画面の表示データ）を根拠にせず、常にサーバー側が保持する商品情報（Sanityから都度取得する改変不可能な情報源）に基づいて行う

**カート画面のグループ表示**

- カートサイドバー・チェックアウト画面は、支払いタイミングが混在する場合のみ「注文時に支払う商品」/「注文後に請求される商品」の2グループに分けて表示し、グループごとの小計を出す。単一タイミングのみの場合は従来通りグループ表示を行わない（決済確定後に初めて分割の事実を知ることがないようにする事前の透明性が目的）

**注文ステータスの遷移（2026-09-13改訂: `paid`までの決済関連の遷移は[[settlement]]へ移管）**

- `orders.status`が本ドキュメントの範囲で直接扱う値は`'cancelled'`（決済単位が作られる前のキャンセル）のみ。それ以外（`'pending_payment'`/`'limit_exceeded'`/`'invoice_sent'`/`'paid'`）は`orders.status`の値ではなく各決済単位（`order_settlements.status`）が取る値になった。`orders.status`はこれらから算出するロールアップ値（[[settlement]]の「`orders.status`のロールアップ算出」参照）
- **`confirming`中の価格交渉工程は2026-09-14撤回**: 要相談商品を含む場合の価格交渉工程（旧`archive/order-flow.md`由来、一時`confirming`状態として復元・明文化していた）は、要相談商品自体をVer1で扱わないと決定したため不要になった（[[catalog]]参照）。将来要相談商品を実装する際に、あらためて調達フロー側で設計し直す
- 注文確定と同時に決済単位の作成に進む（[[settlement]]）。**法人組織の承認待ち・却下という中間状態は2026-09-13廃止**（上記「扱わないこと」参照）。法人会員・個人会員の区別なく、注文確定後は即座に決済フェーズへ進む
- `orders.status`の更新は、必ず`order_status_changes`（追記専用ログ、`from_status`/`to_status`/`changed_by`（`customer`/`admin`/`system`）/`reason`）へのINSERTと同一トランザクションで行う

**月次仕入れ上限チェック（2026-09-13改訂: 実行タイミング・判定ロジックの正は[[settlement]]へ移管）**

- 判定は決済単位（`order_settlements`）ごとに独立して行う。詳細なタイミング（Checkout決済単位の作成時／Invoice決済単位の請求金額入力時）と、all-or-nothingの判定をやめた経緯は[[settlement]]「月次仕入れ上限チェック」参照
- 判定のスコープ（個人か組織か）は[[membership]]が定義する個人/法人の排他性に従う
- キャンセルされた注文は、キャンセルされた時点以降の判定から自動的に除外される（都度再集計するため、能動的な「解放」処理は不要）

**住所の確定**

- チェックアウト画面では、登録済み住所がない状態からの新規入力、登録済み住所がある状態からの選択のいずれの経路でも注文を確定できる。どちらの経路でも確定した住所情報は`shipping_address_snapshot`/`billing_address_snapshot`として注文にスナップショットされ、以後`addresses`側の変更・削除の影響を受けない
- 法人組織のメンバーは、個人の住所帳とは別の組織の共有住所帳（`addresses.organization_id`が非NULL）からも選択できる。同じ組織の他のメンバーが登録した住所も選択対象に含まれる

**注文明細のスナップショット化**

- 商品はSanity CMS側にありSupabaseへFK参照できないため、`order_items`は`sanity_product_id`（TEXT）に加え、商品名・単価・ブランドID/名・発注拠点区分（`fulfillment_location_code`）を注文確定時点の値としてスナップショットする。以後Sanity側で商品名変更・削除・ブランド再割当が起きても過去注文の表示・発注拠点の判定は変わらない
- **要相談商品向けの`negotiated_unit_price`列はVer1では使わない**（2026-09-14）。Ver1は全商品が固定価格のため、`unit_price_snapshot`が注文確定時点で必ず確定している

**通知**

- ステータス変更はメール通知＋マイページ表示の両方で行う。Invoiceフローの請求書メール（Stripeが会員へ自動送信）を除き、全メールをResendで自前実装する。会員向けはマイページリンク、運営者向けは管理画面リンクを含める

### まだ決まっていない・要確認事項

- 🔲 **abandoned なCheckoutの自動キャンセル**: Checkout Session作成から30分以内に`checkout.session.completed`が届かない場合、`pending_payment`の注文を`cancelled`に更新するバッチが未実装（`archive/order-flow.md`ではフェーズ2として言及されているのみ）
- ✅ ~~キャンセル・返金時の払い戻し方針~~（2026-09-14解決）: 顧客都合のキャンセル・返品は原則不可、不良品・誤配送のみ[[returns]]のパターン②③で対応する方針を確定。詳細は[[returns]]参照
- 🔲 **在庫切れ商品のチェックアウト時の挙動**: `out_of_stock`商品がカートに残っている状態でのチェックアウト時の扱いは`specs/003-checkout-invoice-e2e`でスコープ外とされたまま未検討
- ✅ ~~Invoiceの支払い期限~~（2026-09-21解決）: デフォルト7日固定は実装済みと検証済み。「運営者が個別に変更できる」機能は未実装で、追加するかは保留のまま7日固定で実装を進める（issue #224参照）

## 他コンテキストとの関係

- [[settlement]]（2026-09-13新設）: 決済フローの自動分岐（Checkout／Invoice）、決済単位ごとの状態遷移、月次仕入れ上限チェックの実行タイミングは[[settlement]]の責務。本ドキュメントは「支払いタイミングで明細を`at_order`/`after_order`に分類するところまで」に閉じる
- [[procurement]]: 決済単位が`paid`に達した後、商品明細（`order_items`）が発注タスクへどうまとめられ、発注〜入荷がどう進むかは[[procurement]]の責務。`orders.procurement_due_at`は注文確定時にどう計算されるか（未確定）という点で本ドキュメントにも関わるが、値の意味・用途自体は[[procurement]]が定義する
- `fulfillment.md`（未着手）: 梱包・分割出荷・配送状況（`shipments`）は扱わない。商品ごとの`fulfillment_location_code`は`order_items`にスナップショットされるが、それを使って出荷がどう作られるかは`fulfillment.md`の責務
- `returns.md`（未着手）: 発注・配送済み商品の返品・返金は扱わない。注文確定時のキャンセル・返金方針（未確定事項）は将来`returns.md`との境界を明確にする必要がある
- [[subscription-billing]]: ランク・月次仕入れ上限の定義・金額計算そのものはこちらの責務。本ドキュメントは注文確定時点の`rank_code_at_order`/`monthly_limit_at_order`としてスナップショットする側であり、上限判定のロジック自体（7ランクの上限値・確定金額計算）の正はそちらにある
- [[catalog]]: カートに入れる前の商品閲覧・価格計算・支払いタイミング属性（`payment_timing`）の設定は扱わない。本ドキュメントはカートに入った後の商品情報を注文明細としてスナップショットするところから始まる
- [[membership]]: 法人組織の作成・メンバー招待・`org:admin`/`org:member`ロールの定義そのものは扱わない。退会ブロック条件（`paid`以降の注文有無）の判定基準になる注文ステータスの定義は本ドキュメントが正
- `admin-rbac.md`: 運営スタッフ（請求顧客担当等）がInvoice発行・注文管理画面で何を実行できるかの権限マトリクスの正はそちら。本ドキュメントはその権限が使われた結果として注文がどう遷移するか（業務ルール）のみを扱う
