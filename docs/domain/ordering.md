# カート・注文・Checkout/Invoice・法人承認（Ordering）

## このコンテキストの責務

このドキュメントは「会員がカートに商品を入れてから、注文が`paid`（入金確認済み）に達するまで、注文というものがどう成立し、どう状態遷移するか」を定義する。

**扱うこと**:

- カート（`cart_items`）に商品を入れる〜注文確定（`place-order`）までの一連の操作
- 決済フローの自動分岐（Checkoutフロー／Invoiceフロー）と、その根拠になる商品属性（`is_negotiable`・`payment_timing`）
- 支払いタイミングが混在するカートのチェックアウト分割（`split_group_id`）とカート画面のグループ表示
- 注文確定時の住所スナップショット化（新規入力／登録済み住所の選択、個人の住所帳／組織の共有住所帳）
- 月次仕入れ上限チェック（注文確定時・Invoice発行時の2箇所、個人／組織スコープの解決）
- 法人組織の注文承認フロー（一般担当者の発注→承認待ち→管理者の承認/却下）
- 注文ステータス（`orders.status`）の`paid`到達までの遷移と、Stripe Webhookによる自動更新
- 注文明細（`order_items`）への商品情報スナップショット化（商品名・単価・ブランド・発注拠点）
- ステータス変更の追記専用ログ（`order_status_changes`）とメール通知

**扱わないこと**:

- `paid`到達**後**の商品明細ごとの発注・入荷の進捗は[[procurement]]が扱う。本ドキュメントは注文が`paid`に達するところまでで終わり、`orders.status`はそこから先へ進まない（`'sourcing'`/`'ordered'`/`'preparing'`等の値は廃止済み。[[procurement]]参照）
- 梱包・分割出荷・配送状況（`shipments`）は`fulfillment.md`（未着手）が扱う
- 発注済み商品の返品・返金は`returns.md`（未着手）が扱う
- 会員ランクの定義・序列・月次仕入れ上限の金額そのものは[[subscription-billing]]が扱う。本ドキュメントはランク・上限額を「注文確定時点の値としてスナップショットする」ところまでを扱い、値そのものの計算根拠には立ち入らない
- 商品情報（価格・在庫状況・要相談商品かどうか・支払いタイミング属性の設定）そのものの管理は[[catalog]]が扱う。本ドキュメントはカートに入った後の商品情報をスナップショットとして扱うのみ
- 法人組織の作成・メンバー招待・`org:admin`/`org:member`ロールが何者かという定義そのものは[[membership]]が扱う。本ドキュメントは「`org:admin`のみが注文を承認できる」という承認フロー上のルールのみを扱う
- 運営スタッフ（管理者・請求顧客担当・調達担当）が何を実行できるかの権限マトリクスは`admin-rbac.md`が扱う

## 主要な概念・用語

`docs/glossary.md`の「カート・注文・決済」節は現行実装と乖離した旧5ランクモデル時代の記述だったため、本ドキュメント執筆に合わせて更新する（後述）。

| 用語                                 | 定義                                                                                                                                                                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **カート**                           | 購入前に商品を一時的に保存する場所。DB上は`cart_items`（`user_id`, `sanity_product_id`, `quantity`）。注文確定前は何度でも自由に変更でき、スナップショット化されない                                                     |
| **Checkoutフロー**                   | カート内の全商品が注文時払い（`payment_timing='at_order'`）の場合に採用される決済フロー。Stripe Checkoutで即時決済し、運営者の決済作業はゼロ                                                                             |
| **Invoiceフロー**                    | カートに注文後払い（`payment_timing='after_order'`）の商品が1つでも含まれる場合に採用される決済フロー。運営者が内容確認後にStripe Invoiceを手動発行する                                                                  |
| **要相談商品**                       | 価格が個別見積もりとなる商品（`is_negotiable`）。支払いタイミングは常に`after_order`に固定される（[[catalog]]参照）                                                                                                      |
| **チェックアウト分割**               | カートに注文時払い商品と注文後払い商品が混在する場合、1回のチェックアウト操作から2件の`orders`（`checkout`用・`invoice`用）を自動生成すること。同一チェックアウト由来であることは`split_group_id`で関連付ける            |
| **注文（Order）**                    | カートの内容を確定して決済手続きを開始した記録。DB上は`orders`の1行。個人・法人、Checkout・Invoiceいずれのフローも同じテーブル・同じ`status`遷移で扱う                                                                   |
| **注文明細（OrderItem）**            | 注文に含まれる商品ごとの内訳。DB上は`order_items`。商品名・単価・ブランド・発注拠点を注文確定時点の値としてスナップショットする（[[catalog]]の商品データとは別に保持）                                                   |
| **住所スナップショット**             | 注文確定時点の配送先・請求先住所を`orders.shipping_address_snapshot`/`billing_address_snapshot`（JSONB）に複製したもの。以後`addresses`側の住所が変更・削除されても注文の記録は変わらない                                |
| **承認待ち（`pending_approval`）**   | 法人組織の一般担当者（`org:member`）が発注した注文が、管理者（`org:admin`）の承認を待っている状態。決済・請求の手続きは一切開始されない                                                                                  |
| **自動承認（`auto_approved`）**      | 法人組織の管理者（`org:admin`）自身が発注した場合、承認待ちを経由せず即座に通常の決済・請求フローに進む状態                                                                                                              |
| **月次仕入れ上限チェック**           | 注文確定時（固定価格分のみ、または全額）・Invoice発行時（全額）に行う、月間仕入れ上限との突合。個人会員はユーザー単位、法人会員は組織単位で判定する（[[subscription-billing]]）                                          |
| **発注期限（`procurement_due_at`）** | 注文に含まれる商品を配送SLAに間に合わせるためにいつまでに一次卸業者へ発注すべきかの期限。値の用途・使われ方の正は[[procurement]]にあるが、いつ・どう計算されるかは本ドキュメントの範囲内（現状は未確定でNULLのまま許容） |

## 業務ルール・不変条件

### 確定しているもの

**決済フローの分岐**

- 決済フローはカート内商品の`payment_timing`（[[catalog]]で定義）で自動判定する。要相談商品（`is_negotiable=true`）は常に`payment_timing='after_order'`に固定されているため、混在時の判定に個別の特例分岐は不要
- カートが単一の支払いタイミングのみで構成される場合、従来通り1件の注文のみが作成される。`split_group_id`は`NULL`のまま
- 支払いタイミングが混在する場合、チェックアウト時に自動的に2件の`orders`（Checkout用・Invoice用）に分割される。生成された2件は同一の`split_group_id`を持つ。分割対象になった注文は必ず`payment_flow`が異なる2件（`checkout`と`invoice`）が揃う前提であり、2区分を超える分割は想定しない
- チェックアウト分割の振り分け判定は、会員が閲覧・操作できる情報（カート画面の表示データ）を根拠にせず、常にサーバー側が保持する商品情報（Sanityから都度取得する改変不可能な情報源）に基づいて行う
- 分割によって生成される2件の`orders`行の保存は、両方成功するか両方成立しないかのいずれかで、一方のみが記録される状態を許さない（同一トランザクション、または補償処理で保証する）

**カート画面のグループ表示**

- カートサイドバー・チェックアウト画面は、支払いタイミングが混在する場合のみ「注文時に支払う商品」/「注文後に請求される商品」の2グループに分けて表示し、グループごとの小計を出す。単一タイミングのみの場合は従来通りグループ表示を行わない（決済確定後に初めて分割の事実を知ることがないようにする事前の透明性が目的）

**注文ステータスの遷移（`paid`まで）**

- `orders.status`は`'pending_approval'`,`'pending_payment'`,`'confirming'`,`'limit_exceeded'`,`'invoice_sent'`,`'paid'`,`'cancelled'`のいずれかを取る（TEXT+CHECK）。`paid`より先の`'sourcing'`/`'ordered'`/`'preparing'`/`'shipping'`/`'delivered'`は廃止済みで、この列には存在しない（[[procurement]]参照）
- 個人会員のCheckoutフロー: `pending_payment` → (Stripe `checkout.session.completed` Webhook) → `paid`
- 個人会員のInvoiceフロー: `confirming` → (運営者が請求金額入力・上限内) → `invoice_sent` → (Stripe `invoice.paid` Webhook) → `paid`。上限超過時は`confirming` → `limit_exceeded`（会員へ自動メール通知、運営者は再発行不可・手動キャンセルのみ可能）
- 法人組織の一般担当者（`org:member`）が発注した場合: まず`pending_approval`になり、決済・請求の手続きは一切開始されない。管理者（`org:admin`）が承認すると`pending_payment`/`confirming`（既存フローへ直行）に遷移し、以降は個人会員と同じ遷移をたどる。却下すると`cancelled`に遷移し終端状態になる
- 法人組織の管理者（`org:admin`）が発注した場合: 承認待ちを経由せず`auto_approved`のまま即座に`pending_payment`/`confirming`に進む
- 管理者が「承認待ち」の注文を承認する操作を行う際は、発注者（`requested_by_user_id`）が承認時点でもなお当該組織のメンバーであることを再検証しなければならない。除外操作と承認操作がほぼ同時に発生した場合の競合を防ぐため。すでにメンバーでない場合は承認を拒否する
- 一般担当者が「承認待ち」の注文を作成した直後に組織から除外された場合、その注文は却下相当（`cancelled`/`rejected`）として扱う。この時点では決済・請求は一切開始されていないため安全に中断できる
- `orders.status`の更新は、必ず`order_status_changes`（追記専用ログ、`from_status`/`to_status`/`changed_by`（`customer`/`admin`/`system`）/`reason`）へのINSERTと同一トランザクションで行う

**月次仕入れ上限チェック**

- Checkoutフロー: 注文確定時に固定価格商品の合計金額（＝カート全額）で判定する
- Invoiceフロー: 注文確定時は固定価格商品分のみで判定し、要相談商品を含む全額での判定は運営者がInvoice発行時（交渉後価格が確定するタイミング）に改めて行う
- チェックアウト分割が発生する場合でも、月次仕入れ上限は「分割前のカート合計金額（価格が確定している商品のみの合計）」に対して一度だけ判定する。上限を超える場合は分割後のいずれの注文も作成しない（一方のみの作成は許可しない）
- 上限超過時、Checkoutフローは注文レコード自体を作成せずエラー表示のみ行う。Invoiceフローは`limit_exceeded`ステータスの注文として記録し会員へ自動メール通知する（`limit_exceeded`の場合は再通知しない）
- 判定のスコープ（個人か組織か）は[[membership]]が定義する個人/法人の排他性に従う。法人組織の場合、担当者個人ではなく組織の月次使用金額に合算する
- 法人組織の月次上限集計は、却下（`rejected`）された注文を除く`auto_approved`/`pending_approval`/`approved`の全注文金額を合算対象に含める。却下された注文は却下された時点以降の判定から自動的に除外される（都度再集計するため、能動的な「解放」処理は不要）

**住所の確定**

- チェックアウト画面では、登録済み住所がない状態からの新規入力、登録済み住所がある状態からの選択のいずれの経路でも注文を確定できる。どちらの経路でも確定した住所情報は`shipping_address_snapshot`/`billing_address_snapshot`として注文にスナップショットされ、以後`addresses`側の変更・削除の影響を受けない
- 法人組織のメンバーは、個人の住所帳とは別の組織の共有住所帳（`addresses.organization_id`が非NULL）からも選択できる。同じ組織の他のメンバーが登録した住所も選択対象に含まれる

**注文明細のスナップショット化**

- 商品はSanity CMS側にありSupabaseへFK参照できないため、`order_items`は`sanity_product_id`（TEXT）に加え、商品名・単価・ブランドID/名・発注拠点区分（`fulfillment_location_code`）を注文確定時点の値としてスナップショットする。以後Sanity側で商品名変更・削除・ブランド再割当が起きても過去注文の表示・発注拠点の判定は変わらない
- 要相談商品の`unit_price_snapshot`は注文確定時点ではNULL（価格未確定）。運営者がInvoice発行時に確定させた金額は`negotiated_unit_price`に別カラムで記録し、当初見込み額（あれば）と実額を両方追跡できるようにする

**通知**

- ステータス変更はメール通知＋マイページ表示の両方で行う。Invoiceフローの請求書メール（Stripeが会員へ自動送信）を除き、全メールをResendで自前実装する。会員向けはマイページリンク、運営者向けは管理画面リンクを含める

### まだ決まっていない・要確認事項

- 🔲 **abandoned なCheckoutの自動キャンセル**: Checkout Session作成から30分以内に`checkout.session.completed`が届かない場合、`pending_payment`の注文を`cancelled`に更新するバッチが未実装（`archive/order-flow.md`ではフェーズ2として言及されているのみ）
- 🔲 **キャンセル・返金時の払い戻し方針**: 原則返金なしで例外対応は運営者が個別判断（システム外で処理）という旧方針が現行でも有効かは未確認。入金後キャンセルの返金処理フローは`returns.md`（未着手）との切り分けも含めて要検討
- 🔲 **`procurement_due_at`の自動計算ルール**: 配送SLA（何営業日以内に届けるか）から注文確定時に自動計算する想定だが、日数ルールが未確定。ルールが決まるまではNULLのまま許容し、個別に手動で上書きすることも想定する（[[procurement]]と共通の未決事項）
- 🔲 **在庫切れ商品のチェックアウト時の挙動**: `out_of_stock`商品がカートに残っている状態でのチェックアウト時の扱いは`specs/003-checkout-invoice-e2e`でスコープ外とされたまま未検討
- 🔲 **承認待ちの注文が長期間放置された場合の扱い**: 自動失効等の仕組みは`specs/005-b2b-organization`で明示的にスコープ外とされており、別途検討が必要
- 🔲 **Invoiceの支払い期限**: デフォルト7日・運営者が発行時に個別変更可能という旧方針（`archive/order-flow.md`）が現行実装でも維持されているかは未検証

## 他コンテキストとの関係

- [[procurement]]: `orders.status='paid'`に達した後、商品明細（`order_items`）が発注タスクへどうまとめられ、発注〜入荷がどう進むかは[[procurement]]の責務。本ドキュメントは`paid`到達までの承認・支払いフローに閉じる。`orders.procurement_due_at`は注文確定時にどう計算されるか（未確定）という点で本ドキュメントにも関わるが、値の意味・用途自体は[[procurement]]が定義する
- `fulfillment.md`（未着手）: 梱包・分割出荷・配送状況（`shipments`）は扱わない。商品ごとの`fulfillment_location_code`は`order_items`にスナップショットされるが、それを使って出荷がどう作られるかは`fulfillment.md`の責務
- `returns.md`（未着手）: 発注・配送済み商品の返品・返金は扱わない。注文確定時のキャンセル・返金方針（未確定事項）は将来`returns.md`との境界を明確にする必要がある
- [[subscription-billing]]: ランク・月次仕入れ上限の定義・金額計算そのものはこちらの責務。本ドキュメントは注文確定時点の`rank_code_at_order`/`monthly_limit_at_order`としてスナップショットする側であり、上限判定のロジック自体（7ランクの上限値・確定金額計算）の正はそちらにある
- [[catalog]]: カートに入れる前の商品閲覧・価格計算・支払いタイミング属性（`payment_timing`）の設定は扱わない。本ドキュメントはカートに入った後の商品情報を注文明細としてスナップショットするところから始まる
- [[membership]]: 法人組織の作成・メンバー招待・`org:admin`/`org:member`ロールの定義そのものは扱わない。本ドキュメントは「`org:admin`のみが承認できる」という承認フロー上のルール適用のみを扱う。退会ブロック条件（`paid`以降の注文有無）の判定基準になる注文ステータスの定義は本ドキュメントが正
- `admin-rbac.md`: 運営スタッフ（請求顧客担当等）がInvoice発行・注文管理画面で何を実行できるかの権限マトリクスの正はそちら。本ドキュメントはその権限が使われた結果として注文がどう遷移するか（業務ルール）のみを扱う
