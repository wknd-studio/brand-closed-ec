# 発注管理（Procurement）

## このコンテキストの責務

このドキュメントは「顧客の注文が確定した後、運営スタッフ（調達担当）が一次卸業者へどう発注し、その進捗をどう社内で共有するか」を定義する。

**扱うこと**:

- 発注タスク（`procurement_tasks`）による、複数の顧客注文にまたがる同一商品のまとめ発注
- 発注タスクのステータス（未着手/着手中/発注済み/取消）と、複数の運営スタッフ間での二重対応防止
- 明細ごとの入荷記録（`order_items.received_at`）と、部分入荷（同じタスクの中でも明細ごとに届くタイミングが異なる）への対応
- 「まだどのタスクにも入っていない、対応待ちの注文明細」をキューとして扱う考え方（キューへの入場タイミングそのものは[[settlement]]が定義する。本ドキュメントはキューに入った後、どう並べ・どう捌くかを扱う）
- 調達担当が担う作業範囲（発注確定・入荷検品まで）

**扱わないこと**:

- 顧客からみた注文そのものの状態遷移（承認・支払い・キャンセル、`orders.status`）は[[ordering]]（未着手）が扱う。本ドキュメントが起点にするのは、注文が`paid`（入金確認済み）に達した**後**の商品明細（`order_items`）の話であり、`paid`に至るまでの経緯には立ち入らない
- 入荷後の梱包・発送・配送状況（`shipments`）は`fulfillment.md`（未着手）が扱う。本ドキュメントは`order_items.received_at`（明細単位）または`procurement_tasks.ordered_at`（タスク単位）が入るところまでで、その先に`shipments`がどう作られるかは`fulfillment.md`の責務
- 「調達担当ロールが何をしてよいか」という権限の定義そのものは[[admin-rbac]]が扱う。本ドキュメントは権限マトリクスの結果として何が起きるか（業務ルール）のみを扱う
- 返品・返金（発注済み商品に欠陥があった場合の顧客への返金等）は`returns.md`（未着手）が扱う
- 仕入れ先（一次卸業者）そのもののマスタ管理・API連携による自動発注は**意図的にスコープ外**（後述「まだ決まっていない・要確認事項」参照）

## 主要な概念・用語

`docs/glossary.md`には現時点で発注管理まわりの用語が存在しないため、以下はすべて新規定義であり`glossary.md`側への追記が必要。

| 用語                                                                            | 定義                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **発注タスク**                                                                  | 運営スタッフが一次卸業者へ発注する作業単位。DB上は`procurement_tasks`の1行。複数の顧客注文にまたがる同一商品の明細をまとめて1つの発注タスクにできる                                                                                                                                         |
| **対応待ちキュー**                                                              | `order_items.procurement_task_id IS NULL`の明細の集合。まだどの発注タスクにも入っていない、発注担当が次に着手すべき明細を指す。入場するタイミングは`payment_timing`によって異なる（後述、[[settlement]]参照）                                                                               |
| **着手（`claimed`）**                                                           | あるスタッフが発注タスクに対応中であることを宣言し、他のスタッフによる重複対応を防ぐ状態。`assigned_admin_user_id`が埋まる                                                                                                                                                                  |
| **一次卸業者**                                                                  | 商品を実際に仕入れる先。メーカー担当者への直接連絡、またはメーカーが用意する仕入れサイト経由で発注する。API連携は存在せず、発注行為そのものは人手で行う                                                                                                                                     |
| **発注期限（`procurement_due_at`、2026-09-13: V1では使わない方針に変更）**      | ~~注文（`orders`）に含まれる商品を、配送SLAに間に合わせるためにいつまでに一次卸業者へ発注すべきかの期限。発注タスクのキュー表示を並び替える起点として使う~~ 顧客への配送日数のお約束（SLA）自体が現状存在しないため、この列・自動計算ロジックはV1では作らない。並び順は後述の通り単純化する |
| **発注拠点（`fulfillment_location_code`）**                                     | 商品が事務所経由（`office`）か仕入れ先直送（`supplier_direct`）かを表す区分。この区分により、明細が入荷検品（`received_at`）を経由する必要があるかどうかが分岐する（詳細は[[fulfillment]]）                                                                                                 |
| **入荷（`order_items.received_at`、2026-09-19: タスク単位から明細単位に変更）** | 事務所経由の商品が実際に届き、検品を終えたことを記録するタイムスタンプ。**タスクではなく明細ごとに個別に記録する**（後述「部分入荷への対応」参照）                                                                                                                                          |

## 業務ルール・不変条件

### 確定しているもの

- **`procurement_tasks`は「発注を実行する」ためのテーブルではない**。実際の発注行為（電話・仕入れサイトでの操作）は引き続き人手で行う。ソフトウェアが支援するのは、まとめ発注による発注回数の削減と、複数スタッフ間での進捗共有（誰が・どこまで対応したか）に限られる
- **タスクは4ステータス制（2026-09-19改訂: `received`をタスクから削除）**: `pending`（未着手）→`claimed`（担当者が着手中）→`ordered`（発注済み）、および`cancelled`（取消）。`claimed`が二重着手防止の要であり、`assigned_admin_user_id`は`pending`のうちはNULL。**「発注する」は複数の明細に対して常に1回・同時にしか起きない行為なのでタスク側が持つ**
- **部分入荷への対応: 入荷はタスクではなく明細単位で記録する（2026-09-19確定）**: 「発注する」と違い、「実際に届く」ことは、まとめた明細ごとにバラバラのタイミングで起こりうる（例: 3顧客分まとめて3個発注したが、仕入れ先から2個は先に届き、1個は後日という回答があった）。旧設計では`procurement_tasks.received_at`というタスク単位の1つのタイムスタンプしか持たず、一部だけ届いた状態を表現できなかった。新設計では`order_items.received_at`を明細ごとに個別に記録し、届いた明細から順に次のフェーズ（[[fulfillment]]の出荷可能キュー）へ進められるようにする。タスク自体は「発注済み（`ordered`）」であることだけを表し、実際に届いたかどうかは明細側が管理する
- **入荷検品で不良品が見つかった場合、`received_at`は記録しない**: 受領を記録するのは、実際に商品を確認して問題ないと判断したときだけとする。不良品と判明した場合は`received_at`を空のまま、運営者が仕入れ先へ連絡して代替品を手配し、代替品が届いてから初めて記録する。新しいステータスやテーブルは設けず、既存の「受領済みの定義」を厳密にするだけで対応する
- **対応待ちキューへの入場条件は`payment_timing`で異なる（2026-09-13、[[settlement]]の設計に対応）**: `payment_timing='at_order'`の明細は、自分の属する決済単位が`paid`になってから対応待ちキューに入る（支払いが先）。`'after_order'`の明細は注文確定と同時に対応待ちキューに入り、支払いは運営者が後から任意のタイミングで発生させる（調達の方が支払いより先に進むことが普通に起こる）
- **まとめ発注の単位はスタッフの手動選択**: 対応待ちキュー（`procurement_task_id IS NULL`の明細）から、同じブランド・同じ商品のものをスタッフが選んで新しい発注タスクを1件作成し、選んだ明細の`procurement_task_id`をまとめて更新する。ブランドと一次卸業者が1:1かどうかの前提は置かず（後述）、自動でタスク化される仕組みは持たない
- **キューの並び順は「対応待ちになった順（古い順）」のみ（2026-09-13確定）**: 顧客への配送日数のお約束（SLA）が現状存在しないため、`procurement_due_at`のような期限ベースの優先度計算はV1では作らない。担当の割り振りも自動最適化は行わず、早い者勝ちで手を挙げる（`claimed`）方式のまま。配送日数の保証を始める、あるいはスタッフの専門分野・負荷分散による自動割り振りが必要になった時点で改めて設計する
- **集計値はキャッシュしない**: 商品ごとの合計必要数は、タスクに紐づく`order_items`を`sanity_product_id`ごとに`SUM`して都度算出する。表示が重くなった場合のみ、後からキャッシュ列を追加する
- **1明細は同時に1つの発注タスクにしか属さない**: `order_items.procurement_task_id`は単一FK。同じ明細の数量をさらに分割して入荷を分ける運用（例: 5個のうち3個だけ先に受領扱いにする）は当面想定しない。明細単位の`received_at`はあくまで「その明細1行が丸ごと届いたかどうか」のみを表す
- **発注拠点による分岐**: `fulfillment_location_code`（＝参照先`locations.requires_receiving`）が`true`（事務所経由）の商品は、その明細自身の`order_items.received_at`が入って初めて出荷（`shipments`）を作成できる。`false`（仕入れ先直送）の商品は`received_at`を経由せず、タスクの`ordered_at`（仕入れ先へ発注した時点）が入った段階で出荷を作成できる。出荷作成そのものの詳細は[[fulfillment]]の責務
- **RLS・書き込み経路**: 顧客はこのテーブルを一切参照できない（発注業務は運営内部の情報）。運営スタッフ向けのSELECT/INSERT/UPDATEは、RLSポリシーを積み増すのではなく管理画面API（service role経由）に一本化し、そのAPI内で`has({ permission: 'org:orders:manage' })`相当のチェックを行う（判定基準の正は[[admin-rbac]]）。`order_items.procurement_task_id`／`received_at`の更新（タスクへの明細の割り当て・入荷記録）も同じAPI経由に統一する
- **旧オペレーションフローからの変更点**: `archive/operations-order.md`（凍結済み）では`orders.status`が単一の値で`paid`→`sourcing`→`ordered`→`preparing`→`shipping`→`delivered`と遷移し、調達担当が各遷移ボタンを押す運用だった。新設計では1注文に含まれる商品が別々のタイミングで発注・入荷されうることを踏まえ、`orders.status`は`paid`から先に進まなくなり（`'sourcing'`/`'ordered'`/`'preparing'`等の値は廃止）、商品明細単位の進捗は`procurement_tasks`（発注〜入荷）と`shipments`（梱包〜配送、[[fulfillment]]の責務）に分離された。**調達担当が担う作業内容（仕入れ先への発注・納期確認・検品）自体は旧オペレーションマニュアルと変わらない**。運用手順書自体の全面改訂は本ドキュメントのスコープ外（後述）

### まだ決まっていない・要確認事項

- 🔲 **仕入れ先マスタ・API自動発注（`suppliers`）**: 発注方法は商品ごとに異なり（メーカー担当者への直接連絡／仕入れサイト経由）、卸業者側とのAPI連携は現状存在せず今後も予定しない前提だが、将来必要になった場合は`suppliers`テーブルを新設し`procurement_tasks`に`supplier_id`を追加する形で拡張できる（`db-schema-redesign.md`「スコープ外とした論点」）
- 🔲 **ブランドと一次卸業者が1対1かどうか**: 1ブランドが複数卸業者から仕入れられる、または1卸業者が複数ブランドを扱う、といったケースの有無は前提を置いていない。`brand_id_snapshot`はタスク作成時にスタッフが商品をまとめる際の目印として使うだけで、タスク自体を特定のブランドに縛るFK制約は設けない
- ✅ ~~`procurement_due_at`の自動計算ルール~~（2026-09-13解決）: V1では作らない。配送日数のお約束（SLA）を始めるタイミングで、商品データ（カタログ）に仕入れ日数を持たせた上で改めて設計する
- 🔲 **発注タスク一覧UIの並び替え・緊急度表示の実装詳細**: 「対応待ちになった順」で並べる方針は決まっているが、画面上の具体的な見せ方は未定
- 🔲 **`archive/operations-order.md`の全面改訂**: 同ドキュメントは旧・単一`orders.status`遷移を前提にした運用手順書であり、新設計（`procurement_tasks`/`shipments`単位の進捗管理）に合わせた改訂が別途必要。本ドキュメントは「業務ドメインとしてどう定義されているか」までを扱い、運営スタッフ向けの操作手順書の改訂そのものはスコープ外（`docs/domain/README.md`の`specs/`との違い参照）

## 他コンテキストとの関係

- [[ordering]]（未着手）: `orders.status='paid'`に達するまでの承認・支払いフローは[[ordering]]の責務。本ドキュメントは`paid`到達後の`order_items`を起点にする。`orders.procurement_due_at`は注文確定時にどう計算されるかという点で[[ordering]]側の実装とも関わるが、値そのものの意味・用途（発注タスクの並び替え起点）は本ドキュメントが定義する
- [[fulfillment]]（未着手）: 明細の`order_items.received_at`（事務所経由）またはタスクの`ordered_at`（仕入れ先直送）が入った時点から先、`shipments`がどう作られ、梱包・発送・配達完了までどう進むかは[[fulfillment]]の責務。`fulfillment_location_code`／`locations.requires_receiving`という区分の値そのものの定義は[[fulfillment]]側にあり、本ドキュメントはその値によって発注タスクの運用がどう分岐するかを扱うのみ
- [[admin-rbac]]: 「調達担当」ロールが発注タスクに対して何を実行できるか（着手・発注確定・入荷記録）の権限マトリクスの正は[[admin-rbac]]にある。本ドキュメントはその権限が実際の業務でどう使われるかを定義する
- `catalog.md`（未着手）: `order_items.sanity_product_id`／`brand_id_snapshot`の元になる商品・ブランドマスタはSanity側にあり、`catalog.md`の管掌。本ドキュメントはあくまで発注済み・注文済みの商品明細のスナップショットを扱う
- `returns.md`（未着手）: 仕入れ先から届いた商品に不良があった場合の顧客への返品・返金対応は`returns.md`が扱う。発注タスクの検品自体（`received_at`前の仕入れ先とのやり取り）は本ドキュメントの範囲内だが、検品後に顧客対応が必要になった場合の返金フローには立ち入らない
