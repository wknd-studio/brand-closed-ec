# 返品・返金（Returns）

## このコンテキストの責務

このドキュメントは「支払いが完了した注文に対して、会員への返金がどう発生し、どう処理されるか」を定義する。

**扱うこと**:

- 支払い済み注文のキャンセル・返品を「返金」という1つの事象として扱う`returns`／`return_items`のライフサイクル
- 商品の返送を伴うかどうかで分岐する2つのパターン（支払い後・未発送でのキャンセル／発送後の返品）
- 1回の返品・返金申請が複数の注文明細にまたがる場合の扱い（部分返品・一部数量のみの返品）
- 最終的にStripeへのRefund実行に帰着する、というCheckout/Invoice両フロー共通の考え方

**扱わないこと**:

- 支払い前のキャンセル（`orders.status='cancelled'`のみで完結し`returns`を使わないパターン）は[[ordering]]の注文状態遷移の一部として扱う。本ドキュメントが起点にするのは、注文が既に「支払い済み」に達している場合のみ
- 返品対象商品の物理的な受領作業（入荷検品・保管場所への搬入）そのものの手順は[[fulfillment]]寄りの実務だが、本ドキュメント執筆時点でその受け皿となる仕組み（着払い伝票の発行方法・受領場所）は未設計（後述「まだ決まっていない・要確認事項」）
- 仕入れ先起因の不良品について一次卸業者へクレームを入れる・代替品を再発注する業務は`procurement.md`の責務。本ドキュメントは会員への返金という結果のみを扱い、仕入れ先との交渉には立ち入らない
- 「誰が返品を承認してよいか」という権限の定義そのものは[[admin-rbac]]が扱う（ただし本ドキュメント執筆時点で権限マトリクスへの追加が未反映。後述）

## 主要な概念・用語

`docs/glossary.md`には現時点で返品・返金まわりの用語が存在しないため、以下はすべて新規定義であり`glossary.md`側への追記が必要。

| 用語                                        | 定義                                                                                                                                                             |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **返品・返金申請**                          | 会員が起点となって開始する、支払い済み注文への返金プロセス。DB上は`returns`の1行                                                                                 |
| **返品明細**                                | 1回の返品・返金申請に含まれる、元の注文明細（`order_items`）ごとの内訳。DB上は`return_items`の1行。数量指定により一部数量のみの返品を表現できる                  |
| **支払い後・未発送キャンセル（パターン②）** | 支払いは完了したが、商品はまだ会員の手元に届いていない状態でのキャンセル。返送物が存在しないため`returns.status`は`received`を経由しない                         |
| **発送後の返品（パターン③）**               | 不良品・誤配送等、商品が既に会員の手元へ届いた後に発生する返品。`returns.status`が`received`（返送受領）を経由してから返金に進む                                 |
| **返金確定**                                | 運営者がStripe側でRefundを実行し、`returns.stripe_refund_id`／`refund_amount`／`refunded_at`が確定する時点。これをもって返品・返金申請のライフサイクルが完了する |

## 業務ルール・不変条件

### 確定しているもの

- **支払い前のキャンセルは`returns`を使わない**: 「支払い」も「商品の返送」も発生していない場合（支払い前キャンセル＝パターン①）は、単に`orders.status='cancelled'`にするだけで完結する。`returns`が対象にするのは、支払いが発生した後の2パターン（②支払い後・未発送でのキャンセル、③発送後の返品）のみ
- **返送の有無で`received`ステップの通過が分岐する**: パターン②（未発送）は返送物が存在しないため`approved`から直接`refunded`へ進み、`received_at`は常にNULLのまま。パターン③（発送後）のみ`received`（返送受領）を経由する
- **6ステータス制**: `requested`（申請）→`approved`／`rejected`（承認/却下）→（パターン③のみ）`received`（返送受領）→`refunded`（返金完了）、および`cancelled`（申請自体の取消）。`orders.status`とは独立したライフサイクルとして`returns.status`が管理する
- **決済単位（`checkout`/`invoice`）の違いによる分岐は持たない**: 返品・返金が発生する時点では、いずれの決済単位に属する明細も既に「支払い済み（`paid`）」であるという前提は共通のため、`flow`による処理分岐は設けない。返金額算出時に参照する単価は`order_items.unit_price_snapshot`（2026-09-14: 要相談商品はVer1では扱わないため、`negotiated_unit_price`列は現時点で使わない。[[catalog]]・[[settlement]]参照）
- **最終的にStripeへの単一のRefund実行に帰着する**: パターン②③のどちらも、会員への返金という結果はStripe Refund APIの実行という同じ処理で完結するため、`returns`テーブルを分けない
- **1回の申請は複数の注文明細にまたがりうる**: `orders`/`order_items`と同じ多対1の構造を`returns`/`return_items`でも踏襲する。`return_items.quantity`により、注文明細の数量の一部のみを返品する（例: 3枚のうち1枚のみ）ことも表現できる。`order_items.quantity`以下であることの検証はアプリケーション層で行う
- **`stripe_refund_id`はUNIQUE制約で二重返金を防ぐ**: 同じ返品・返金申請に対してRefundを重複実行しないためのべき等性キーとして機能する
- **顧客からの直接書き込みは`requested`状態のINSERTのみ**: 承認・却下・返金実行（`status`の`requested`以降への遷移、`stripe_refund_id`/`refund_amount`のセット）は管理画面API（service role経由）に一本化し、顧客からの直接UPDATEは許可しない。「返品したい」という申請の起点だけは顧客の操作として認める（`procurement_tasks`等、他の運営専用テーブルとは異なる点）
- **旧オペレーションフローからの変更点**: `archive/operations-order.md`（凍結済み）9-4節では、`paid`以降のキャンセルは「管理者のみ」がStripeダッシュボードで直接Refundを実行し、返金理由や金額をシステム外（口頭・手動記録）で管理する運用だった。新設計では`returns`/`return_items`という正式なエンティティに申請内容・承認者・理由・返金額を記録することで、この一連の経緯をシステム上で追跡できるようにする。**Refundの実行主体がStripeであること自体は変わらない**（本ドキュメントが定義するのは、その前後の申請・承認・記録のプロセス）
- **顧客都合のキャンセル・返品は原則不可（2026-09-14確定）**: 御社は在庫を持たない受注発注型モデルであり、一度仕入れ先へ正式発注した商品は返品されても在庫として再利用できない。加えてStripeは返金してもカード決済手数料が返ってこないため、安易な返品受付はそのまま損失になる。よって`approved`にするかどうかの判断基準は「不良品・誤配送など運営側／仕入れ先側に起因する理由か」に限定する。この基準そのものはシステムで強制せず、運営者の承認判断に委ねる（旧`archive/order-flow.md`の「原則返金なし、例外は運営者が個別判断」という方針と、正式な申請フローとして記録する新設計は矛盾しない）
- **返送の物流フロー（2026-09-14確定: システムでは深追いしない）**: 返送先住所は新しい概念を持たず、既存の`locations`の`'office'`をそのまま使う。着払い伝票を発行するか、先払いの返送ラベルを送るか、後日返送料を精算するかという具体的な方法は運営者の裁量とし、システムには`returns`に自由記述の備考欄（`admin_note`等）を1つ用意するだけにとどめる。返送料は御社負担とする（顧客都合の返品ではないため）。実際の顧客への案内は個別のメール対応とし、配送業者API連携は行わない（[[procurement]]の仕入れ先対応と同じ「システムは記録の受け皿、実務は人手」という考え方）
- **返品・返金の承認権限は管理者ロールのみ（2026-09-14確定）**: `archive/operations-order.md`の運用（`paid`以降のキャンセルは管理者のみ）をそのまま踏襲する。返金はお金が動く例外対応であり、権限を広げる理由がないため、請求・顧客担当等には開放しない（[[admin-rbac]]の権限マトリクスへの反映が必要）
- **返品受付期間はシステムでハード制限しない（2026-09-14確定）**: 「商品到着から30日」を運用上の目安とするが、これを超えても運営者の判断で承認できる余地を残す。返品自体が例外対応である以上、日数で機械的に締め切る設計にはしない
- **返金額は単価×数量のみ（2026-09-14確定）**: 現状のスキーマに送料を別建てで徴収する仕組みが存在しないため、返金額算出に送料は関与しない。将来送料を別徴収するようになった場合は改めて設計する
- **申請取消（`cancelled`）の運用（2026-09-14確定）**: 顧客本人は`requested`のまま（運営者がまだ`approved`/`rejected`にしていない）間だけ取り消せる。運営者は権限がある限りどの状態からでも取消可能とする
- **パターン②承認時、進行中の調達作業と連動する（2026-09-14確定）**: 対象明細の発注タスク（`procurement_tasks`）が`pending`/`claimed`（まだ仕入れ先に正式発注していない）であれば、返品の承認と同時にその明細をタスクから自動的に外す（同じタスクに他の明細がまとめられていれば、それらには影響しない。この明細だけがそのタスクの対象だった場合はタスク自体も`cancelled`にする）。**`ordered`（正式発注済み）まで進んでいる場合、システムはブロックせず「すでに仕入れ先へ発注済みです」という警告を表示するだけに留め、承認するかどうかの最終判断は運営者に委ねる**（仕入れ先との調整は電話等の人手作業のため）
  - **`ordered`の場合の「外す」操作は自動実行せず、運営者が後から明示的に行う**: 承認時点では明細とタスクの紐付けはそのまま残す。運営者が仕入れ先と交渉し（数量を減らしてもらう、または諦めて損失計上する等）対応が済んだ後、`pending`/`claimed`の場合と同じ「タスクから外す」操作を、運営者が任意のタイミングで手動実行する。新しい操作は増やさず、実行するタイミングを自動／手動で切り替えるだけ
  - **この設計はERP・MRP（生産管理）システムの「発注統合（PO Consolidation）」における標準的な扱いと一致する**: 発注がベンダーに未送信なら自動で数量調整、送信済みなら「行き場のない需要（orphaned demand）」としてフラグを立てるだけに留め、実際の変更交渉は担当者に委ねるという業界標準パターンをそのまま踏襲している
- **仕入れ先起因の不良品は専用の連携を作らない（2026-09-14確定）**: 仕入れ先へのクレーム対応自体は運営者の人手作業とし、代替品の手配が必要な場合は既存の「まとめ発注」の仕組みで通常通り新しい発注タスクを手動作成する。`returns`から`procurement_tasks`への専用リンクは設けない

### まだ決まっていない・要確認事項

（2026-09-14時点で残っている項目なし。旧「`return_items`が参照する在庫の扱い」は、御社が無在庫転売型モデル（会員の注文後に運営者が仕入れ先へ発注する）であり在庫という概念自体を持たないため、そもそも問い自体が成立しないと判明し削除した）

## 他コンテキストとの関係

- [[ordering]]: `orders.status='paid'`に達するまでの承認・支払いフロー、および支払い前キャンセル（パターン①、`returns`を使わない）は[[ordering]]の責務。本ドキュメントは`paid`到達後に発生する返金のみを扱う
- [[fulfillment]]: 発送後の返品（パターン③）における返送先住所は既存の`locations`の`'office'`をそのまま使う（新しい概念は追加しない）。`shipments`自体のキャンセル・巻き戻し処理は[[fulfillment]]の範囲外で、本ドキュメントが定義する`returns`のライフサイクルの中で扱う
- [[procurement]]: パターン②の返品承認時、対象明細の発注タスクが`pending`/`claimed`であればタスクから自動的に外し、`ordered`まで進んでいれば警告表示のみで運営者の判断に委ねる（上記「確定しているもの」参照）。仕入れ先起因の不良品への代替品手配は、[[procurement]]の既存の「まとめ発注」の仕組みで運営者が手動対応し、専用の連携は設けない
- [[admin-rbac]]: 返品・返金の承認は管理者ロールのみに限定する（上記「確定しているもの」参照）。権限マトリクスへの反映が必要
- `catalog.md`: `return_items`が参照する`order_items.sanity_product_id`／単価スナップショットの元になる商品マスタはSanity側にあり、`catalog.md`の管掌。本ドキュメントは発注済み・注文済みの商品明細に対する返金のみを扱う
