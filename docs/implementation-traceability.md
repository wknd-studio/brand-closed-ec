# 実装状況トレーサビリティの仕組み

機能が増え、`service-spec.md` の仕様変更も頻繁に発生する中で、「今どこまで実装されているか」を実際にサービスを動かさずに把握できるようにするための仕組み（ハーネス）を定義する。

---

## 全体像

```
docs/service-spec.md          … 何を作るべきか（唯一の仕様源）
        │  /spec-sync（差分検知 → 変更提案レポート）
        ▼
Linear issues (BRAND-XX)      … 何を作ると決め、今どこまで進んだか
        │  Linear公式の GitHub 連携（PRマージで自動 Done 化）
        ▼
コード + E2Eテスト             … 実際に動作が保証されているか
        （クリティカルフローはテストタイトルに BRAND-XX を埋め込む）
```

3つの層それぞれが「ズレを検知・防止する仕組み」を持つことで、どの層を見ても実装状況を追えるようにする。

---

## 層ごとの役割

### ① 仕様 ⇔ Linear（`service-spec.md` ⇔ BRAND issues）

- **役割**: 仕様変更が起きたときに、対応する Linear issue の起票漏れ・前提の陳腐化を検知する
- **仕組み**: `/spec-sync` スキル（`.claude/skills/spec-sync/SKILL.md`）
  - 前回同期地点（`.claude/spec-sync-state.json`）から `docs/service-spec.md` の差分を取り、Linear の BRAND issue 一覧と突き合わせる
  - 🆕 仕様にあるが issue がない項目 / ⚠️ 既存 issue の前提が古い項目 をレポートする
  - Linear への書き込みは行わず、ユーザー承認後にのみ反映する
- **運用**: `docs/service-spec.md` を変更したら `/spec-sync` を呼ぶ

### ② Linear ⇔ コード（BRAND issues ⇔ PR）

- **役割**: 「Done」ステータスが実態（マージ済みか）とズレないようにする
- **仕組み**: Linear 公式の GitHub 連携機能
  - ブランチ名または PR に issue ID（`BRAND-XX`）を含めることで自動リンクされ、PR マージ時に issue が自動的に Done へ遷移する
  - カスタムスクリプト（GitHub Actions 等）は不要。過去に同等機能を独自実装しようとした issue（BRAND-8）は、この公式連携で代替できるためキャンセル済み
- **運用**: 実装ブランチ名・PR に issue ID を必ず含める（本リポジトリでは元々の運用ルール）

### ③ コード ⇔ E2E テスト

- **役割**: 「動くとされているもの」が実際に動作することを保証し、テストタイトル自体を実装状況の一覧として使えるようにする
- **仕組み**（今後整備）:
  - クリティカルな業務フロー（認証・チェックアウト・退会・プラン変更等）の E2E テストに、対応する story ID を埋め込む
    ```ts
    test.describe("AUTH-05: 退会", () => { ... });
    ```
  - `grep -r "BRAND-XX" tests/e2e/` で、そのストーリーがテストされているかを機械的に確認できる
- **現状**: BRAND-90（チェックアウト E2E）・BRAND-91（住所管理 E2E）が未着手。今後書く E2E から ID タグ付けを徹底する

### ④ 突合レポート（①〜③の整合性チェック）

- **役割**: 「Linear で Done になっているクリティカルフローに、対応する E2E テストが存在しない」というズレを検出する
- **現状**: 未着手。③のID タグ付けが一定数貯まった段階で、Done issue 一覧と `tests/e2e/` 内の ID 参照を突き合わせる簡易チェック（スクリプト or 手動確認）を検討する

---

## まとめ

| 層                | 目的                                   | 状態                                  |
| ----------------- | -------------------------------------- | ------------------------------------- |
| ① 仕様 ⇔ Linear   | 仕様変更の起票漏れ・陳腐化を防ぐ       | `/spec-sync` 運用開始                 |
| ② Linear ⇔ コード | Done ステータスの信頼性を保つ          | Linear 公式連携で稼働中               |
| ③ コード ⇔ E2E    | 「動く」の保証とテストによる実装一覧化 | クリティカルフローから着手予定        |
| ④ 突合レポート    | ①〜③のズレを機械的に検出する           | 未着手（③がある程度貯まってから検討） |
