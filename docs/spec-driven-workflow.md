# 仕様駆動開発ワークフロー

> **ステータス: 設計確定。導入作業中**。「仕様⇄チケット⇄コード」のズレのうち、特に③（仕様変更が実装タスクに繋がらず放置される問題）を解決するための設計。主要な論点はすべて合意済み（末尾「論点と決定事項」参照）。spec-kit本体・`constitution.md`・Linear連携スキルは導入済み。GitHub PRレビュー導線（`CODEOWNERS`等）を本ドキュメントの更新と合わせて整備中。`specs/` フォルダはまだ0件で、初回featureの起票（`/speckit-specify`）は別途実施する。

---

## 背景・課題

`docs/service-spec.md` の運用の中で、以下3種類のズレが発生することが分かった。

1. **仕様→チケットのズレ**: 仕様変更に対応するLinear issueが起票されない
2. **ドキュメント同士のズレ**: `service-spec.md` は更新したが、`glossary.md` 等の関連ドキュメントが古いまま残る
3. **仕様→コードのズレ**: 仕様変更（事業判断）が実装タスクとして誰にも認識されず、コードが追いつかないまま放置される（実例: 7ランクモデルへの移行が未着手のまま発覚した件、BRAND-97）

①②は「`/spec-sync` ・`/doc-audit` スキルの打ち忘れ」で説明がつくが、これは**スキルが任意実行である限り再発する**。③はより根が深く、「仕様を変更したら実装タスクが必要」という認識自体が漏れる、プロジェクト管理上の問題。

これを事後チェックではなく、**そもそも仕様変更が実装タスクを生まずには終われない仕組み**にすることで解決する。

## リポジトリ構成（確定）

```
memory/constitution.md    ← プロジェクトの不変原則（技術スタック制約・ブランチ戦略等）
specs/                    ← spec-kitが管理する「変更の履歴」置き場
  001-invite-system/
    spec.md               ← WHAT/WHY + 受け入れ条件
    plan.md               ← 技術計画
    tasks.md              ← タスク分解
  002-seven-rank-pricing/
    spec.md
    plan.md
    tasks.md
  ...
docs/                     ← 「特定の変更に属さない」横断的な参照資料だけを残す
  overview.md              ← 今の全体像の索引（薄い。トピックごとに最新のspecsフォルダへリンクするだけ。事実は書き写さない）
  glossary.md              ← 用語集
  product-vision.md        ← プロダクトビジョン
  definition-of-done.md    ← 完了の定義
  collaboration.md         ← 協業ガイド
  adr/                     ← 技術決定record
```

`service-spec.md` ・`user-stories.md` ・`data-model.md` ・`order-flow.md` ・`operations-order.md` は役目を終える。今後の変更はすべて `specs/` 配下に積み上がっていく。既存内容の移行方法は「未決定の論点」参照。

## ワークフロー（具体例: 「プランを7段階に増やしたい」の場合）

### フェーズ1: 要望が生まれる

|                | 動き                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| ビジネスサイド | 「プランをもっと細かく分けたい」と考え、エンジニア側に伝える（普段の会議・Slack等、今と同じ） |
| 技術者サイド   | 話を聞くだけ。まだ何もしない                                                                  |

### フェーズ2: 仕様を文章に起こす

|                | 動き                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 技術者サイド   | `/specify` で `specs/NNN-topic/spec.md` を作成する。「何を」「なぜ」やるかと受け入れ条件をまとめる |
| ビジネスサイド | まだ何もしなくていい                                                                               |

### フェーズ3: ビジネスサイドに自動で届く

|                | 動き                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 技術者サイド   | PRを作成するだけ。「共有する」作業を意識的に行う必要はない                                                                                      |
| ビジネスサイド | 何もしなくても、`spec.md` を含むPRが作られた時点でCODEOWNERSにより自動でレビュー依頼メールが届く（`plan.md`・`tasks.md`だけの変更では届かない） |

### フェーズ4: レビュー・すり合わせ

|                | 動き                                                                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ビジネスサイド | 届いたメールからPRを開き、`spec.md` をブランチ上のファイルとして（diffではなく）読み、「Conversation」タブにコメントを書く。承認ボタンのような手続きは不要 |
| 技術者サイド   | `/clarify` でコメント・曖昧な点を解消し、`spec.md` を更新する。更新すれば同じPRに積まれ、再度レビュー依頼が届く（フェーズ3に戻る）                         |

### フェーズ5: 実装計画に落とす

|                | 動き                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 技術者サイド   | `/plan` → `plan.md`、`/tasks` → `tasks.md` を生成する。続けて自作の橋渡しスキルで `tasks.md` からLinear issueを起票する |
| ビジネスサイド | 関与しない（見たければ見られるが必須ではない）                                                                          |

### フェーズ6: 開発が進む

|                | 動き                                                           |
| -------------- | -------------------------------------------------------------- |
| 技術者サイド   | Linear issueをもとに、既存のTDD/PRフローで実装する             |
| ビジネスサイド | 普段通りLinear・ステージング環境で進捗を確認できる（変化なし） |

### フェーズ7: 完成

|                | 動き                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 技術者サイド   | コードがマージされると、チケットは自動で完了になる（今と同じ仕組み）。あわせて `docs/overview.md` の該当トピックのリンクを最新の `specs/NNN-topic/` に更新する |
| ビジネスサイド | 完成したものをステージングで確認する（変化なし）                                                                                                               |

## 今と何が変わるか

- **ビジネスサイド**: やることはほぼ増えない。「仕様が変わったら自動的に読める画面に届き、コメントできる」という受け身の体験が増えるだけ
- **技術者サイド**: `service-spec.md` を直接書き換える作業が、spec-kitの `/specify` `/clarify` `/plan` `/tasks` という一連のコマンドを通す作業に変わる。これが一番大きな変化

## 論点と決定事項

### ① 「今の全体像」をどこで見るか — 解決済み

`docs/overview.md` という薄い索引ドキュメントを置き、トピックごとに最新の `specs/NNN-xxx/spec.md` をリンクする方式に決定（事実は書き写さない）。

### ② 通知手段 — 解決済み（GitBookからGitHubに変更）

当初はGitBook（Git Sync）でのビジネス閲覧・通知を想定していたが、有料サービスであるため不採用とし、追加コストなしで使えるGitHub標準機能に変更した。

- `.github/CODEOWNERS` に `specs/**/spec.md @レビュアーのGitHubハンドル` と記載し、`spec.md` を含むPRが作成された時点で自動的にレビューを依頼する（`plan.md`・`tasks.md` のみの変更は技術者向けのため対象外とし、無関係な通知を防ぐ）
- 通知はGitHub標準の「レビュー依頼されました」メールをそのまま使う（追加連携不要）
- ビジネスサイドの各レビュアーは、リポジトリ閲覧用に招待済みのGitHubアカウント（`collaboration.md` 参照）をそのまま使う。新規アカウント作成は不要
- 閲覧時はPRの「Files changed」タブの差分ではなく、該当ブランチの `spec.md` をファイルとして開く（レンダリング表示されるため、diffの行番号・色付きは見えない）。コメントは「Conversation」タブの通常コメントに書く
- Google Chatへの中継が必要になった場合は、GitHubのWebhook経由での中継を別途検討する

### ③ 既存ドキュメントとの関係 — 解決済み

`service-spec.md` ・`user-stories.md` ・`data-model.md` ・`order-flow.md` ・`operations-order.md` は役目を終え、`specs/` に一本化する。`glossary.md` ・`product-vision.md` ・`definition-of-done.md` ・`collaboration.md` ・`adr/` は特定の変更に属さない横断的な資料として `docs/` に残す。

**`memory/constitution.md` と `CLAUDE.md` の役割分担**:

spec-kitの `/plan` コマンドは実行のたびに `.specify/memory/constitution.md` を読み込み、生成した技術計画が原則に沿っているかを確認する「Constitution Check」を必須ステップとして実行する仕組みになっている（spec-kit本体のテンプレートに組み込まれた機能であり、単なるドキュメントではない）。したがって空にはできない。

一方、Claude Codeは`/plan`実行時も含め常にCLAUDE.mdをコンテキストに持っている。CLAUDE.mdの内容を`constitution.md`に複製すると「2箇所に書いて片方が古くなる」問題を再発させるため、以下の役割分担にする。

- **CLAUDE.md**: 唯一の正。ブランチ戦略・PRサイズ・テスト自動選択ルール・コミット形式等のエンジニアリング制約と、Claude Codeの振る舞いルール（理解度チェック・言語指定等）を持つ。今と変更しない
- **`memory/constitution.md`**: CLAUDE.mdの内容は複製せず、「この計画がCLAUDE.mdの各ルールに沿っているか確認せよ」という参照指示のみ記載する。加えて、CLAUDE.mdの管轄に含まれない**spec-kit固有の原則**（`spec.md`に受け入れ条件を必ず明記する、曖昧な点は`/clarify`を経ないと`/plan`に進めない、等）を持つ

既存5ファイルの中身（実装済みの内容）を遡って `specs/000-xxx/` として作り直すか、歴史的記録としてアーカイブするだけにするかは、導入作業時に決める。

### ④ Linearとの連携方法 — 解決済み

`tasks.md` を読んでLinear issueを起票する自作スキルを新設する（`mcp__linear__save_issue` を使用）。spec-kit本体が直接サポートしない、このリポジトリ固有の配線として自作する。
