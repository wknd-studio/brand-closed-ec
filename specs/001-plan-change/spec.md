# Feature Specification: プラン変更（アップグレード・ダウングレード）

**Feature Branch**: `001-plan-change`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "会員が自分でプランのアップグレード・ダウングレードを行えるようにしたい。アップグレードは即時反映し、その場で仕入れ上限がリセットされる。ダウングレードは当月の仕入れ計画を壊さないよう、当月末まで現プランを維持し、翌月から新プランに切り替える。（参考: docs/archive/user-stories.md の PLAN-01・PLAN-02、docs/plan-change-flow.md）"

## Clarifications

### Session 2026-07-17

- Q: 初期費用の差分請求ってどういう意味ですか？（PR #84のConversationコメントより） → A: アップグレード時に請求するのは「新プランの初期費用」まるごとではなく、「新プランの初期費用 − これまでに支払った中で一番高いランクの初期費用」の差額だけ、という意味。例: STARTER登録時に初期費用¥5,000を支払った会員がPROプラン（初期費用¥50,000）にアップグレードすると、差額の¥45,000だけが請求される。過去に支払い済みの金額以下のランクへ変更する場合は追加請求されない

## User Scenarios & Testing _(mandatory)_

### User Story 1 - プランのアップグレード (Priority: P1)

会員が、より多くの商品を仕入れられるようにするために、現在契約中のプランから上位のプランに自分でアップグレードする。

**Why this priority**: 仕入れ上限に達した会員が上位プランに切り替えられないと、その場で機会損失（仕入れたくても仕入れられない）が発生する。アップグレードは即時性の価値が最も高く、単独でも成立するためP1とする。

**Independent Test**: 現在のプランで月次仕入れ上限に近い会員が、上位プランへのアップグレードを申請し、即座に仕入れ上限が新プランの値に更新されることを確認する。ダウングレード機能がなくても単独でテスト・提供可能。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 会員がプラン変更画面を開いている, **When** 上位プランを選択する, **Then** 変更後の月額費用・月間仕入れ上限・機能差分が変更確定前に表示される
2. **Given** 会員が上位プランへのアップグレードを申請している, **When** 変更内容を確認する, **Then** 「新プランの初期費用 − これまでに支払った中で一番高いランクの初期費用」の差額（例: STARTER登録時に¥5,000支払い済みの会員がPRO（初期費用¥50,000）にアップグレードする場合は差額¥45,000）が発生する場合はその金額が明示される
3. **Given** 過去に支払い済みの最高ランク以下のプランへ変更する（ダウングレード後の再アップグレード等）, **When** 変更内容を確認する, **Then** 初期費用は発生しない旨が示される
4. **Given** 会員が上位プランへのアップグレードを確定する, **When** 確定操作を行う, **Then** 即座にランクが切り替わり、当月の仕入れ上限が新プランの上限にリセットされた状態で表示される
5. **Given** ENTERPRISEプランへの変更を検討している会員, **When** プラン一覧を見る, **Then** ENTERPRISEは選択肢に表示されず、個別問い合わせの案内が表示される

_システムが保証すること_

1. アップグレード確定と同時に会員のランクを更新し、当月の仕入れ計画期間の起点を変更日にリセットする（前の期間の使用済み金額は新しい期間に引き継がない）
2. 初期費用は「新プランの初期費用 − 支払い済み最高ランク（`initial_fee_paid_rank`）の初期費用」の差分のみ請求し、差分が0以下の場合は請求しない
3. アップグレード操作は決済手段が未登録の会員に対して決済手段登録を先に案内する

---

### User Story 2 - プランのダウングレード (Priority: P2)

会員が、月額費用を抑えるために、現在契約中のプランから下位のプランに自分でダウングレードする。ただし、当月の仕入れ計画を壊さないよう、変更は当月末まで反映を待つ。

**Why this priority**: コスト最適化のための機能であり、緊急性はアップグレードより低い。またアップグレードのフロー（プラン変更画面・比較表示）に依存するためP2とする。

**Independent Test**: 上位プランを契約中の会員が下位プランへのダウングレードを申請し、当月中は現行プランの仕入れ上限が維持されたまま、翌月になった時点で自動的に新プランへ切り替わることを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 会員がプラン変更画面を開いている, **When** 下位プランを選択する, **Then** 変更後の月額費用と、適用開始が「当月末（次の更新日）から」であることが確定前に表示される
2. **Given** 会員がダウングレードを確定する, **When** 確定操作を行う, **Then** 当月中は現在のプラン・仕入れ上限のまま変わらない旨が表示される
3. **Given** ダウングレードを予約した会員が、期日前に別のプランへ変更したい, **When** プラン変更画面を再度開く, **Then** 予約中のダウングレード内容を確認・変更できる
4. **Given** 会員が最下位プラン（STARTER）へダウングレードを申請する, **When** 変更内容を確認する, **Then** 他のダウングレードと同様に期末適用である旨が表示される（STARTERも有料プランであり、退会（解約）とは別の操作）

_システムが保証すること_

1. ダウングレード確定時点ではランク・仕入れ上限を変更せず、当月の請求期間が終了した時点で自動的に新プランへ切り替える
2. 当月中に仕入れ上限に関する警告は表示しない（現プランの上限が期末まで維持されるため）
3. ダウングレード予約中に会員が別プランへの変更・予約取り消しを行った場合、直前の予約内容を新しい内容で上書きする

---

### Edge Cases

- ダウングレード予約中の会員が、予約とは異なる上位プランへアップグレードした場合、ダウングレード予約は取り消され、通常のアップグレードとして即時処理される
- ダウングレード予約中の会員が、現在契約中のプランと同じプランを再度選択した場合、ダウングレード予約が取り消されるだけで、プラン自体は変わらない
- 同じプランを重複して選択した場合（変更なし）は何も起きない
- 月の途中でアップグレードした会員が、同月中にさらにアップグレードした場合も、その都度即時反映・上限リセットが行われる

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: システムは会員がプラン変更画面で現在のプランと変更候補プランの月額費用・月間仕入れ上限・機能差分を比較できるようにしなければならない
- **FR-002**: システムはアップグレードを即時反映し、確定と同時に当月の仕入れ上限を新プランの値にリセットしなければならない
- **FR-003**: システムはダウングレードを当月の請求期間終了時点まで反映を遅らせ、それまでは現行プランの仕入れ上限を維持しなければならない
- **FR-004**: システムはアップグレード時、「新プランの初期費用 − これまでに支払った中で一番高いランクの初期費用」の差額のみを初期費用として請求しなければならない（差額が0以下の場合は請求しない。例: STARTER登録時に¥5,000支払い済みの会員がPRO（初期費用¥50,000）にアップグレードする場合は差額¥45,000のみ請求し、その後BASICにダウングレードしても追加請求は発生しない）
- **FR-005**: システムはダウングレード予約中の会員が予約内容を確認・変更・取り消しできるようにしなければならない
- **FR-006**: システムはENTERPRISEプランへの変更を会員によるセルフサービスの選択肢から除外しなければならない（個別契約が必要なため）
- **FR-007**: システムは決済手段未登録の会員が有料プランへアップグレードしようとした場合、決済手段登録を先に案内しなければならない

### Key Entities

- **会員ランク（Plan）**: 会員が契約するプランの段階。月額費用・月間仕入れ上限・初期費用の要否を持つ
- **月次仕入れ枠（Monthly Limit）**: 会員ランクごとに定まる、当月に仕入れ可能な金額の上限。請求期間の起点日を基準に算出される
- **プラン変更予約（Pending Plan Change）**: ダウングレード確定時に作成される、期末に適用予定の変更内容。会員は期末までいつでも内容を確認・変更・取り消しできる

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 会員はアップグレード確定操作の完了から1分以内に、新しい仕入れ上限が反映された状態でプラン変更後の画面を確認できる
- **SC-002**: ダウングレード予約後、期末までの期間中に仕入れ上限に関する問い合わせ（サポート対応）が発生しない
- **SC-003**: プラン変更（アップグレード・ダウングレード双方）を、会員がサポート担当者を介さずセルフサービスで完了できる割合が100%になる

## Assumptions

- 会員は既にいずれかの有料プラン（STARTER以上）でStripeの継続課金契約を持っている（初回のプラン契約・招待登録時のプラン選択自体は別機能の範囲）
- 初期費用の金額・プランごとの月間仕入れ上限の具体的な数値は `docs/archive/service-spec.md` を正とし、本仕様では書き写さない
- ダウングレード予約の取り消し・変更操作の具体的なUI導線は、実装計画（`/speckit-plan`）側で検討する
- 決済手段の登録フロー自体はAUTH系の既存仕様に従う（本仕様の範囲外）
