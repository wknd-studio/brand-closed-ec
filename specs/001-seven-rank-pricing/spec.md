# Feature Specification: 7ランクモデルへの移行

**Feature Branch**: `001-seven-rank-pricing`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "サービス仕様書（docs/archive/service-spec.md）で確定している7ランクの会員プランモデル（STARTER/BASIC/STANDARD/PRO/ADVANCED/PREMIUM/ENTERPRISE）に、現行の5ランクモデル（free/entry/standard/pro/enterprise）から移行したい。会員登録時のプラン選択・商品カタログの閲覧制限・月次仕入れ上限のチェック・注文確定時のランクスナップショットなど、既存のランクを参照している全ての会員体験が、新しい7ランクの値でこれまで通り正しく動作することを保証する。これは新しい顧客機能の追加ではなく、既存の値・ロジックを新モデルに置き換える移行作業である。（参考: docs/archive/service-spec.md の「会員プラン」セクション）"

**性質に関する注記**: 本featureは新しい顧客向け機能の追加ではなく、既存の値・型を新モデルに置き換える横断的な移行である。そのため、ユーザーストーリーは「独立してデプロイ可能な新機能」ではなく「移行後も既存の会員体験が壊れていないことを保証する対象領域」として整理する。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 会員登録・オンボーディングでのプラン選択 (Priority: P1)

新規会員が登録時に、7ランクの中から希望のプランを選択して登録できる。

**Why this priority**: 新規登録が止まると事業影響が最も大きい。他のどの領域よりも優先して壊れていないことを確認する必要がある。

**Independent Test**: 新規会員登録フローで7ランクのいずれかを選択し、選択したランクで登録が完了することを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 新規登録者がプラン選択画面を開いている, **When** 画面を見る, **Then** STARTER〜PREMIUMの6ランクが選択肢として表示される（ENTERPRISEはセルフサービスの対象外）
2. **Given** 登録者がいずれかのプランを選択する, **When** 登録を完了する, **Then** 選択したプランの月額費用・初期費用に応じた決済（Stripe）が行われる

_システムが保証すること_

1. 登録完了時に会員のランクが選択された7ランクのいずれかとしてDBに保存される
2. 初期費用は選択したランクの金額が正しく請求される

---

### User Story 2 - 商品カタログの閲覧・購入制限 (Priority: P1)

会員が商品カタログを閲覧する際、自分のランクでアクセス可能な商品のみ閲覧・購入できる。

**Why this priority**: カタログ制限が壊れると、閲覧できるはずの商品が見えない、または本来閲覧できない商品が見えてしまう（会員体験・ビジネスルール違反の両面でリスクが高い）ため、登録と同等の優先度とする。

**Independent Test**: 各ランクの会員でカタログを閲覧し、そのランクでアクセス可能な商品のみ表示されることを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** STARTERランクの会員がカタログを閲覧している, **When** 上位ランク限定商品のページを開こうとする, **Then** 閲覧できない旨が表示される
2. **Given** PREMIUMランクの会員がカタログを閲覧している, **When** 商品一覧を見る, **Then** 自ランク以下がアクセス可能な商品はすべて表示される

_システムが保証すること_

1. 商品ごとに設定された最低アクセスランクと、会員の現在のランクを7ランクの序列で比較し、アクセス可否を判定する
2. 商品ごとの掛け率（割引率）が会員のランクに応じて正しく適用される

---

### User Story 3 - 月次仕入れ上限のチェック (Priority: P1)

会員がカート・注文確定時に、自分のランクの月間仕入れ上限に基づいて上限超過が正しく判定される。

**Why this priority**: 上限判定はStripeへの実際の請求・注文確定に直結するため、登録・カタログと同等に優先度が高い。

**Independent Test**: 各ランクの会員で、上限に近い金額のカートを作成し、上限超過判定が新ランクの上限値で正しく行われることを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 会員が自分のランクの月間仕入れ上限に近い金額をカートに入れている, **When** 上限を超える注文を確定しようとする, **Then** 上限超過の旨が表示される

_システムが保証すること_

1. 月次仕入れ上限のチェックは、会員の現在のランクに対応する新しい上限値を参照する
2. 上限値は `docs/archive/service-spec.md` の「料金・仕入れ上限」表を単一の情報源とし、コード側に重複して書き写さない

---

### User Story 4 - 注文確定時のランクスナップショット (Priority: P2)

注文確定後にランクが変更されても、注文時点のランク・上限値が正しく記録され続ける。

**Why this priority**: 過去の注文データの整合性に関わるが、リアルタイムの会員体験には直接影響しないためP2とする。

**Independent Test**: 注文を確定した後に会員のランクを変更し、確定済みの注文の`rankAtOrder`が変更前の値のまま保持されることを確認する。

**Acceptance Scenarios**（受け入れ条件）

_運営者が確認できること_

1. **Given** 会員が注文を確定した後にランクを変更する, **When** 管理画面で過去の注文を確認する, **Then** 注文確定時点のランク（新7ランクの値）が表示される

_システムが保証すること_

1. 注文確定時に会員の現在のランクを7ランクの値でスナップショットとして記録する

---

### Edge Cases

- Stripe側の価格（Price ID）が7ランク分正しく用意されていない状態で登録・変更が行われた場合、エラーとして扱い決済に進ませない
- 移行時点で既存会員が持っている旧ランクの値をどう新ランクに対応させるか（データ移行）は、本featureの実装計画で扱う
- ENTERPRISEランクは個別契約のため、本featureのセルフサービスフロー（登録・カタログ・上限チェック）の対象外とし、既存の管理者による個別設定フローを維持する

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: システムは会員登録・オンボーディング画面でSTARTER〜PREMIUMの6ランクを選択肢として表示しなければならない（ENTERPRISEを除く）
- **FR-002**: システムは商品ごとの最低アクセスランクと会員のランクを、新7ランクの序列（STARTER < BASIC < STANDARD < PRO < ADVANCED < PREMIUM < ENTERPRISE）で比較しなければならない
- **FR-003**: システムは月次仕入れ上限のチェックを、会員の現在のランクに対応する新しい上限値で行わなければならない
- **FR-004**: システムは商品の掛け率（割引率）を会員のランクに応じて正しく適用しなければならない
- **FR-005**: システムは注文確定時に会員の現在のランク（新7ランクの値）をスナップショットとして記録しなければならない
- **FR-006**: システムはENTERPRISEランクをセルフサービスの選択肢から除外しなければならない（既存の管理者個別設定フローを維持する）

### Key Entities

- **会員ランク（MemberRank）**: STARTER / BASIC / STANDARD / PRO / ADVANCED / PREMIUM / ENTERPRISE の7段階。月額費用・初期費用・月間仕入れ上限・商品掛け率を持つ
- **商品（Product）**: 最低アクセスランク・掛け率を持つ（Sanity CMS管理）
- **注文（Order）**: 確定時点のランクをスナップショットとして保持する

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 移行後、既存の会員登録・カタログ閲覧・注文確定のE2Eテストが全て新ランクの値で通過する
- **SC-002**: 移行によって既存会員が閲覧できる商品範囲・仕入れ上限が意図せず変化する事例が0件である（移行はデータ移行方針に従い、既存会員は事前に合意した対応ランクへ切り替わる）
- **SC-003**: 料金・ランク名・上限値がコード上の単一の定義箇所からのみ参照され、複数箇所への書き写しが0件である

## Assumptions

- 各ランクの月額費用・初期費用・掛け率の具体的な数値は `docs/archive/service-spec.md` を正とし、本仕様では書き写さない（月間仕入れ上限は同ドキュメントで `TBD` のままのため、実装計画までに確定させる）
- 既存会員（旧5ランク）を新7ランクのどれに対応させるかというデータ移行の具体的な対応表は、実装計画（`/speckit-plan`）で扱う
- Stripeの商品・価格（Price ID）は7ランク分の新規作成が必要であり、これは実装のFoundational作業に含まれる
- プラン変更（アップグレード・ダウングレード）の操作自体は別feature（依存元。7ランク移行の完了後に着手）であり、本featureの範囲外
