# Feature Specification: 会員登録・ログインフローのE2Eテスト網羅

**Feature Branch**: `002-e2e-auth-coverage`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "7種類の会員プランでの会員登録フローとログインフローを全てE2Eテストで網羅する。現在のE2Eテスト（tests/e2e/auth/onboarding.spec.ts）はClerkのバックエンドAPIで発行した一回限りのチケットで直接ログイン状態を作っており、実際のログイン画面（メールアドレス・パスワード入力、メールでの2段階認証コード入力）を一度も経由していない。2段階認証はメールに届く6桁コード方式で既に有効になっている。実際のログイン画面・登録画面の操作を経由するテストを追加し、既存の作り込まれていないカバレッジを埋める。"

**実機確認による前提の修正（2026-07-20、T001）**: 実機調査（`research.md`参照）により、(1) 招待リンク経由の登録では招待自体がメール確認済み扱いとなるため確認コード入力が発生しない、(2) ログイン時の追加確認コードは、アカウント単位・インスタンス単位の固定MFA設定ではなく、**Clerkが「そのブラウザ・デバイスがそのアカウントでログインした実績があるか」を見て、見慣れないデバイスからのログインにのみ発動する仕組み**であることが判明した。同一ブラウザで登録直後にログインすると確認コードは要求されないが、別ブラウザ（シークレットウィンドウ等）からログインすると確認コードが要求されることをユーザーが手動確認済み。本featureのログインE2Eテストは、Playwrightの各テストが通常独立したブラウザコンテキストを使うことを利用し、この確認コード要求を正しく再現する。

**性質に関する注記**: 本featureは新しい顧客向け機能の追加ではなく、既存の会員登録・ログイン機能に対する自動テストの網羅性を高める作業である。プロダクトの挙動そのものは変更しない。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 実際の登録画面を経由した新規会員登録 (Priority: P1)

新規会員が、招待リンクから実際の登録画面（利用規約同意→メールアドレス・パスワード入力）を操作して登録を完了し、プランを選択して正しく決済画面まで到達できることをテストで保証する。

**Why this priority**: 会員登録はサービスの入り口であり、実際の画面操作を経由しないテストでは「見た目上動いているように見えるが実際の画面が壊れている」不具合を検知できない。7ランク移行（`specs/001-seven-rank-pricing`）で登録画面のプラン一覧が変わったばかりであり、優先度が最も高い。

**Independent Test**: Clerkのテスト用メールアドレス（`+clerk_test`サブアドレス）を使い、招待URL経由で実際の登録フォームにパスワードを入力して登録を完了できることを、代表プラン1つ（STARTER）で確認する。

**スコープの決定（2026-07-20）**: 当初は6ランク全てを個別にループしてテストする想定だったが、ランクごとの差異（正しいStripe価格に紐づくか等）は`tests/integration/select-plan.test.ts`・`tests/unit/domain/member-rank.test.ts`で既にランク単位に検証済みであり、E2Eで6回繰り返しても追加のリスク検知にはならないと判断した。E2Eレイヤーの役割は「実際のブラウザで登録フォームが壊れていないか」の確認に絞り、代表プラン1つのみとする（CI実行時間・フレーキーさのコストを避けるため）。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 招待リンクから`/welcome`にアクセスしている, **When** 利用規約に同意して次に進む, **Then** Clerkの登録フォーム（パスワード入力欄。招待によりメールアドレスは既に確認済みのため入力欄は表示されない）が表示される
2. **Given** 登録フォームにパスワードを入力して送信する, **When** 登録が完了する, **Then** プラン選択画面（`/onboarding/plan`）へ遷移する
3. **Given** STARTERプランを選択する, **When** 登録を確定する, **Then** Stripe Checkout画面へ遷移する

_システムが保証すること_

1. 登録完了時にDB上の会員レコードが作成され、選択したランクが正しく記録される

### User Story 2 - 実際のログイン画面を経由したログイン（未知デバイスの確認コード込み） (Priority: P1)

既存会員が、実際のログイン画面でメールアドレス・パスワードを入力し、見慣れないブラウザからのアクセス時に表示される確認コードを入力してログインを完了できることをテストで保証する。

**Why this priority**: 現状のE2Eテストは全て`ticket`戦略によるバイパスで、実際のログインフォームの操作・確認コード入力を一度も経由していない。ログインはサービスの入り口の1つであり、画面が壊れていても検知できない状態を解消する優先度が高い。

**Independent Test**: 登録済みのClerkテスト用アカウントに対し、（登録時とは別の）新しいブラウザコンテキストからログイン画面にメールアドレス・パスワードを入力し、確認コード入力画面が表示され、固定値`424242`を入力してログインが完了し、ログイン後の画面（オンボーディング完了済みなら`/shop`）へ到達することを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 見慣れないブラウザから`/sign-in`にアクセスしている, **When** メールアドレス・パスワードを入力して送信する, **Then** 確認コード入力画面が表示される
2. **Given** 正しい確認コードを入力する, **When** ログインが完了する, **Then** 会員向けの画面（オンボーディング完了済みなら`/shop`、未完了なら`/onboarding/plan`）へ遷移する
3. **Given** 誤った確認コードを入力する, **When** 送信する, **Then** エラーメッセージが表示され、ログインが完了しない

_システムが保証すること_

1. 確認コードを正しく入力しない限りセッションが確立されない

### Edge Cases

- 登録テストは、既存の`tests/e2e/auth/onboarding.spec.ts`にある「チケット方式でログイン済み状態から始める」テスト（オンボーディング完了後の画面遷移確認）とは目的が異なるため、両方を残す（本featureは「ログイン過程そのもの」を追加でカバーする。既存テストを置き換えない）
- Clerkのテスト用メールアドレス規約（`+clerk_test`を含むアドレス）を使う
- ENTERPRISEはセルフサービス登録の対象外（FR-006、`specs/001-seven-rank-pricing`）であり、また6ランクの個別検証はユニット・統合テストの担当のため、本featureの登録テストはSTARTERプランのみを対象とする
- 会員登録には管理者が発行した招待コードが必要（招待制クローズドEC）。E2Eテストでは実際に管理者画面を操作するのではなく、管理者画面が内部で使っているものと同じClerk公式バックエンドAPI（`invitations.createInvitation`）をテストの事前準備として直接呼び出し、レスポンスに含まれる招待URL（`url`フィールド）へ直接遷移することで、実際にメールを受信・クリックしたのと同じ状態を再現する
- **ログインテスト用会員は固定アカウントを使う（`research.md`参照）**: ログインの確認コードは「見慣れないデバイスからのアクセス」で発動するため、User Story 2のテスト用会員を都度動的に作成すると、その作成過程（ブラウザ操作）が信頼済みデバイスを作ってしまい、確認コードが再現できなくなる。既存の`onboarding.spec.ts`と同じ固定アカウント（`E2E_USER_EMAIL`/`E2E_USER_PASSWORD`。`+clerk_test`アドレス）を使い回し、ログインは新しいPlaywrightブラウザコンテキストから行う

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: E2Eテストは、Clerkの`ticket`戦略によるバイパスではなく、実際の登録フォーム（招待URL経由でのパスワード入力）を操作して新規登録を完了しなければならない
- **FR-002**: E2Eテストは、代表プラン（STARTER）について、登録フォームの操作からStripe Checkout画面への到達まで確認しなければならない
- **FR-003**: E2Eテストは、実際のログインフォーム（メールアドレス・パスワード入力・確認コード入力）を、登録時とは別のブラウザコンテキストから操作してログインを完了しなければならない
- **FR-004**: 登録テスト・ログインテストで作成したClerkユーザー・DB上の会員レコードは、テスト終了後に必ずクリーンアップしなければならない（CLAUDE.mdのテスト運用ルールに従う）
- **FR-005**: 既存の`tests/e2e/auth/onboarding.spec.ts`（チケット方式による、ログイン後の画面遷移確認）は削除・置き換えず、本featureのテストと共存させる

### Key Entities

- **Clerkテストユーザー**: `+clerk_test`を含むメールアドレスで作成される、招待発行元アプリの操作を経由せずテスト専用に用意されたアカウント

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 代表プランで、実際の登録画面操作からStripe Checkout到達までがE2Eテストで自動検証される
- **SC-002**: 実際のログイン画面操作（メールアドレス・パスワード＋未知デバイス確認コード）がE2Eテストで自動検証される
- **SC-003**: 登録・ログインの実画面を操作するテストが追加されたことで、今後この画面に手を加えた際の壊れを人手の確認なしに検知できる

## Assumptions

- ログイン時の確認コードは、固定のMFA設定ではなく「見慣れないデバイスからのアクセス」に対するClerkのデバイス認識ベースの確認である（T001調査・ユーザーの手動確認により判明。詳細は`research.md`）
- Clerkのテスト用メール規約（`+clerk_test`を含むアドレスは確認コードが固定値`424242`になり、実メールは送信されない）は、本番相当のDevelopmentインスタンスでも有効である
- テスト用メールアドレスのドメイン（`@wknd-studio.com`）は既存の`E2E_USER_EMAIL`と同じものを使う想定
