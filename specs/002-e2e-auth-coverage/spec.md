# Feature Specification: 会員登録・ログインフローのE2Eテスト網羅

**Feature Branch**: `002-e2e-auth-coverage`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "7種類の会員プランでの会員登録フローとログインフローを全てE2Eテストで網羅する。現在のE2Eテスト（tests/e2e/auth/onboarding.spec.ts）はClerkのバックエンドAPIで発行した一回限りのチケットで直接ログイン状態を作っており、実際のログイン画面（メールアドレス・パスワード入力、メールでの2段階認証コード入力）を一度も経由していない。2段階認証はメールに届く6桁コード方式で既に有効になっている。実際のログイン画面・登録画面の操作を経由するテストを追加し、既存の作り込まれていないカバレッジを埋める。"

**性質に関する注記**: 本featureは新しい顧客向け機能の追加ではなく、既存の会員登録・ログイン機能に対する自動テストの網羅性を高める作業である。プロダクトの挙動そのものは変更しない。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 実際の登録画面を経由した新規会員登録（6プラン全て） (Priority: P1)

新規会員が、招待リンクから実際の登録画面（メールアドレス・パスワード入力→メールで届く確認コードの入力）を操作して登録を完了し、STARTER〜PREMIUMの6ランクいずれを選択しても正しく決済画面まで到達できることをテストで保証する。

**Why this priority**: 会員登録はサービスの入り口であり、実際の画面操作を経由しないテストでは「見た目上動いているように見えるが実際の画面が壊れている」不具合を検知できない。7ランク移行（`specs/001-seven-rank-pricing`）で登録画面のプラン一覧が変わったばかりであり、優先度が最も高い。

**Independent Test**: Clerkのテスト用メールアドレス（`+clerk_test`サブアドレス）を使い、実際の登録フォームにメールアドレス・パスワードを入力し、届く確認コードを固定値`424242`で入力して登録を完了できることを、6ランクそれぞれで確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 招待リンクから`/welcome`にアクセスしている, **When** 利用規約に同意して次に進む, **Then** Clerkの登録フォーム（メールアドレス・パスワード入力欄）が表示される
2. **Given** 登録フォームにメールアドレス・パスワードを入力して送信する, **When** 確認コード入力画面が表示される, **Then** 6桁のコード入力欄が表示される
3. **Given** 正しい確認コードを入力する, **When** 登録が完了する, **Then** プラン選択画面（`/onboarding/plan`）へ遷移する
4. **Given** STARTER〜PREMIUMのいずれかのプランを選択する, **When** 登録を確定する, **Then** Stripe Checkout画面へ遷移する

_システムが保証すること_

1. 登録完了時にDB上の会員レコードが作成され、選択したランクが正しく記録される
2. 誤った確認コードを入力した場合はエラーが表示され、登録が完了しない

### User Story 2 - 実際のログイン画面を経由したログイン（メール2段階認証込み） (Priority: P1)

既存会員が、実際のログイン画面でメールアドレス・パスワードを入力し、メールで届く2段階認証コードを入力してログインを完了できることをテストで保証する。

**Why this priority**: 2段階認証は既に有効な本番相当の機能であり、User Story 1と同様にクリティカルな入り口の1つ。現状のE2Eテストは全てこの過程を素通りしており、テストされていない領域として最も優先度が高い。

**Independent Test**: 登録済みのClerkテスト用アカウントで、ログイン画面にメールアドレス・パスワードを入力し、2段階認証コード（固定値`424242`）を入力してログインが完了し、ログイン後の画面（オンボーディング完了済みなら`/shop`）へ到達することを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** `/sign-in`にアクセスしている, **When** メールアドレス・パスワードを入力して送信する, **Then** 2段階認証コード入力画面が表示される
2. **Given** 正しい2段階認証コードを入力する, **When** ログインが完了する, **Then** 会員向けの画面（オンボーディング完了済みなら`/shop`、未完了なら`/onboarding/plan`）へ遷移する
3. **Given** 誤った2段階認証コードを入力する, **When** 送信する, **Then** エラーメッセージが表示され、ログインが完了しない

_システムが保証すること_

1. 2段階認証を正しく完了しない限りセッションが確立されない

### Edge Cases

- 6プランの登録テストは、既存の`tests/e2e/auth/onboarding.spec.ts`にある「チケット方式でログイン済み状態から始める」テスト（オンボーディング完了後の画面遷移確認）とは目的が異なるため、両方を残す（本featureは「ログイン過程そのもの」を追加でカバーする。既存テストを置き換えない）
- Clerkのテスト用メールアドレス規約（`+clerk_test`を含むアドレス）を使うため、プランごとに区別できるサブアドレス（例: `+clerk_test_starter`）を用いて、テスト間でのユーザー重複を避ける
- ENTERPRISEはセルフサービス登録の対象外（FR-006、`specs/001-seven-rank-pricing`）のため、本featureの登録テスト対象は6ランクとする
- 会員登録には管理者が発行した招待コードが必要（招待制クローズドEC）。E2Eテストでは実際に管理者画面を操作するのではなく、管理者画面が内部で使っているものと同じClerk公式バックエンドAPI（`invitations.createInvitation`）をテストの事前準備として直接呼び出し、レスポンスに含まれる招待URL（`url`フィールド）へ直接遷移することで、実際にメールを受信・クリックしたのと同じ状態を再現する

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: E2Eテストは、Clerkの`ticket`戦略によるバイパスではなく、実際の登録フォーム（メールアドレス・パスワード入力・確認コード入力）を操作して新規登録を完了しなければならない
- **FR-002**: E2Eテストは、STARTER・BASIC・STANDARD・PRO・ADVANCED・PREMIUMの6ランクそれぞれについて、登録フォームの操作からStripe Checkout画面への到達まで確認しなければならない
- **FR-003**: E2Eテストは、実際のログインフォーム（メールアドレス・パスワード入力・2段階認証コード入力）を操作してログインを完了しなければならない
- **FR-004**: 登録テスト・ログインテストで作成したClerkユーザー・DB上の会員レコードは、テスト終了後に必ずクリーンアップしなければならない（CLAUDE.mdのテスト運用ルールに従う）
- **FR-005**: 既存の`tests/e2e/auth/onboarding.spec.ts`（チケット方式による、ログイン後の画面遷移確認）は削除・置き換えず、本featureのテストと共存させる

### Key Entities

- **Clerkテストユーザー**: `+clerk_test`を含むメールアドレスで作成される、確認コード・2段階認証コードが固定値`424242`になるテスト専用アカウント

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 6ランク全てで、実際の登録画面操作からStripe Checkout到達までがE2Eテストで自動検証される
- **SC-002**: 実際のログイン画面操作（パスワード＋メール2段階認証）がE2Eテストで自動検証される
- **SC-003**: 登録・ログインの実画面を操作するテストが追加されたことで、今後この画面に手を加えた際の壊れを人手の確認なしに検知できる

## Assumptions

- 2段階認証の方式はメールコードのみで、TOTP（認証アプリ）・SMSコードは現時点で使用していない（本featureはメールコード方式のみを対象とする）
- Clerkのテスト用メール規約（`+clerk_test`を含むアドレスは確認コード・2段階認証コードが固定値`424242`になる）は、本番相当のDevelopmentインスタンスでも有効である
- テスト用メールアドレスのドメイン（`@wknd-studio.com`）は既存の`E2E_USER_EMAIL`と同じものを使う想定
