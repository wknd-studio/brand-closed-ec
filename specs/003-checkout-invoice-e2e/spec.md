# Feature Specification: カタログ〜チェックアウト・決済確定フローのE2Eテスト網羅

**Feature Branch**: `003-checkout-invoice-e2e`

**Created**: 2026-07-20

**Status**: Draft

**Input**: User description: "カタログ閲覧からチェックアウト・決済確定までの一連の会員体験を、実際の画面操作を経由するE2Eテストで網羅する。対象範囲: 商品カタログ閲覧（ブランド一覧・商品一覧・商品詳細）→ カートへの追加 → チェックアウト画面での配送先/請求先住所選択 → 注文確定。注文確定以降、2つの決済フローに分岐する: (1) checkoutフロー（固定価格商品）: 実際のStripe Checkout画面へ遷移し、テストカードで決済 → Stripe webhook処理後に注文ステータスが `paid` になることを確認 (2) invoiceフロー（要相談商品 = is_negotiable商品）: Stripeへのリダイレクトはなく、運営者への通知・会員への確認メール送信を経て `/order/invoice-complete` へ遷移することを確認。配達完了までのステータス遷移（sourcing/ordered/preparing/shipping等）は運営者側の管理画面オペレーションであり、会員の購買フローとは別ドメインのため本featureのスコープ外とする。"

**性質に関する注記**: 本featureは新しい顧客向け機能の追加ではなく、既存の購買機能に対する自動テストの網羅性を高める作業である。プロダクトの挙動そのものは変更しない。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - カタログ閲覧から固定価格商品の決済確定まで (Priority: P1)

会員が、商品カタログを閲覧し、固定価格商品をカートに追加し、チェックアウト画面で配送先・請求先住所を選択して注文を確定すると、実際のStripe Checkout画面へ遷移し、テストカードでの決済後に注文が支払い完了（`paid`）状態になることをテストで保証する。

**Why this priority**: カタログ閲覧から決済完了までは、会員が実際に商品を購入する際の中核となる導線であり、事業収益に直結する。既存のE2Eテスト（`tests/e2e/auth/onboarding.spec.ts`）はプラン選択後にStripe Checkoutへ遷移することのみ確認しており、実際の商品購入導線（カタログ→カート→チェックアウト）は一度も自動テストされていない。

**Independent Test**: 招待経由で登録した会員（`specs/002-e2e-auth-coverage`で確立したパターンを踏襲）が、実際の画面操作でカタログから固定価格商品を選び、（a）登録済み住所がない状態から新規入力する経路、（b）登録済み住所がある状態から選択する経路、の両方で注文を確定し、Stripe Checkout画面でのテストカード決済後、注文が`paid`になることを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 商品カタログ画面にアクセスしている, **When** ブランドを選択する, **Then** そのブランドの商品一覧が表示される
2. **Given** 商品一覧を閲覧している, **When** 商品を選択する, **Then** 商品詳細（価格・在庫状況）が表示される
3. **Given** 固定価格商品をカートに追加している, **When** チェックアウト画面へ進む, **Then** 配送先・請求先住所の選択画面が表示される
4. **Given** 登録済みの住所がない会員がチェックアウト画面にいる, **When** 配送先・請求先の住所入力フォームに入力する, **Then** その住所で注文を確定できる
5. **Given** 登録済みの住所がある会員がチェックアウト画面にいる, **When** 既存の住所を選択する（新規入力せず）, **Then** その住所で注文を確定できる
6. **Given** いずれかの方法で住所を確定して注文を確定する, **When** 注文が確定する, **Then** 実際のStripe Checkout画面へ遷移する
7. **Given** Stripe Checkout画面でテストカードにより決済する, **When** 決済が完了する, **Then** 決済完了後の画面へ遷移する
8. **Given** カート内の固定価格商品の合計が当月の仕入れ上限を超えている, **When** 注文を確定しようとする, **Then** 上限超過のエラーメッセージが表示され、Stripe Checkout画面へは遷移しない

_システムが保証すること_

1. Stripe webhook処理後、対象注文のステータスが`paid`になる（**注記**: 会員向け画面には注文ステータスを表示する画面が現状存在しないため、この検証はDBへの直接照会で行う。詳細はresearch.md参照）
2. 注文確定時にDB上に注文レコード・注文明細が作成される
3. 新規入力した住所・既存住所どちらの経路でも、確定した住所情報が注文の配送先・請求先スナップショットとして正しく記録される
4. 月次仕入れ上限を超過する場合、注文レコードは作成されない

### User Story 2 - 要相談商品の見積依頼から確認完了まで (Priority: P2)

会員が、要相談（`is_negotiable`）商品をカートに追加して注文を確定すると、Stripe Checkoutへのリダイレクトを経由せず、運営者への通知・会員への確認メール送信を経て確認完了画面へ遷移することをテストで保証する。

**Why this priority**: checkoutフローと異なる分岐処理であり、要相談商品の購入導線が壊れていても検知できない状態を解消する。checkoutフローよりも該当する商品数・利用頻度が少ないと想定されるため優先度はP2とする。

**Independent Test**: 招待経由で登録した会員が、要相談商品をカートに追加してチェックアウトを確定し、Stripeへのリダイレクトなしに`/order/invoice-complete`へ遷移することを確認する。

**Acceptance Scenarios**（受け入れ条件）

_会員が確認できること_

1. **Given** 要相談商品をカートに追加している, **When** チェックアウト画面へ進む, **Then** 価格が「要相談」と表示される
2. **Given** 住所を選択して注文を確定する, **When** 注文が確定する, **Then** Stripe Checkout画面へは遷移せず、確認完了画面（`/order/invoice-complete`）へ遷移する

_システムが保証すること_

1. 注文確定時にDB上の注文レコードが`invoice`フロー・`confirming`ステータスで作成される

### Edge Cases

- 配達完了までのステータス遷移（`sourcing`/`ordered`/`preparing`/`shipping`等）は運営者側の管理画面オペレーションであり、会員の購買フローとは別ドメインのため本featureのスコープ外とする
- 月次仕入れ上限のチェックには、注文確定時（checkout/invoice共通、`place-order.ts`の`checkMonthlyLimit`）と、要相談商品の請求書発行時（`issue-invoice.ts`。運営者が交渉後価格を確定するタイミング）の2つの独立したチェック箇所がある。前者（注文確定時、実際のチェックアウト画面操作でエラー表示・非遷移を確認）は本featureのUser Story 1に含める。後者（請求書発行時）は運営者側の管理画面オペレーションのため本featureのスコープ外とし、別issue（`BRAND-137`）として起票済み
- 上限判定ロジック自体の正しさ（7ランクの上限値・確定金額計算等）は`specs/001-seven-rank-pricing`のUser Story 3で既にユニット・統合テストレベルで検証済み。本featureでは「実際のチェックアウト画面を操作した際に正しくブロックされるか」というUI経由の確認のみを追加する
- 商品在庫切れ（`out_of_stock`）商品のチェックアウト時の挙動は本featureのスコープ外とする（別途検討）
- テスト用会員・招待・注文データは`specs/002-e2e-auth-coverage`で確立したクリーンアップパターンを踏襲し、テスト終了後に必ず削除する

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: E2Eテストは、実際のカタログ画面（ブランド一覧・商品一覧・商品詳細）を操作して固定価格商品をカートに追加しなければならない
- **FR-002**: E2Eテストは、実際のチェックアウト画面で配送先・請求先住所を（a）登録済み住所がない状態からの新規入力、（b）登録済み住所がある状態からの選択、の両経路で確定し、注文を確定できなければならない
- **FR-003**: E2Eテストは、固定価格商品の注文確定後、実際のStripe Checkout画面への遷移とテストカードでの決済を操作し、Stripe webhook処理後に注文が`paid`になることを確認しなければならない
- **FR-003a**: E2Eテストは、カート内の固定価格商品の合計が当月の仕入れ上限を超える場合、実際のチェックアウト画面操作でエラーメッセージが表示され、Stripe Checkout画面への遷移も注文レコードの作成もされないことを確認しなければならない
- **FR-004**: E2Eテストは、要相談商品の注文確定後、Stripe Checkoutへのリダイレクトが発生せず`/order/invoice-complete`へ遷移することを確認しなければならない
- **FR-005**: テストで作成したClerkユーザー・DB上の会員レコード・注文レコードは、テスト終了後に必ずクリーンアップしなければならない（CLAUDE.mdのテスト運用ルールに従う）
- **FR-006**: 既存のE2Eテスト（`tests/e2e/auth/`配下）は変更せず、本featureのテストと共存させる

### Key Entities

- **Order（注文）**: `payment_flow`（`checkout`/`invoice`）・`status`（`pending_payment`→`paid`、または`confirming`→`invoice_sent`等）を持つ。本featureでは`paid`または`confirming`到達までを検証範囲とする
- **Product（商品）**: `is_negotiable`フラグにより固定価格商品/要相談商品が区別される。Sanityで管理される

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: カタログ閲覧から固定価格商品の決済完了（`paid`）までがE2Eテストで自動検証される
- **SC-002**: 要相談商品の注文確定から確認完了画面到達までがE2Eテストで自動検証される
- **SC-003**: 月次仕入れ上限超過時に注文確定がブロックされることが、実際のチェックアウト画面操作を通してE2Eテストで自動検証される
- **SC-004**: 購買フローの実画面を操作するテストが追加されたことで、今後この導線に手を加えた際の壊れを人手の確認なしに検知できる

## Assumptions

- 「登録済み住所がある」経路のテストでは、事前準備として実際の住所登録画面を操作するか、Supabaseへ直接住所レコードを作成することで登録済み状態を作る。具体的な準備方法は`/speckit-plan`で確定する
- 注文ステータスの検証は、会員向け画面に該当する表示箇所が存在しないため、Supabaseへの直接照会で行う（管理画面`/admin/orders/[id]`には表示されるが、別セッション・別権限が必要になり複雑化するため採用しない）
- Stripeのテストカード（`4242424242424242`）を使用する
- テスト用メールアドレスは`specs/002-e2e-auth-coverage`と同じ規約（`+clerk_test`を含むアドレス）を使う
- Stripe webhookの処理完了を待つため、E2Eテストにはポーリングまたは十分なタイムアウトが必要になる
