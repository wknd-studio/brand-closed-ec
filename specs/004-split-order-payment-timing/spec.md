# Feature Specification: 商品別支払いタイミング設定とカート分割注文

**Feature Branch**: `004-split-order-payment-timing`

**Created**: 2026-07-31

**Status**: Draft

**Input**: User description: "商品ごとに支払いタイミング(注文時払い/注文後払い)を設定できるようにし、カートに両方の商品が混在する場合は自動で2つの注文に分割する機能。現在は商品のis_negotiable(価格未確定)フラグのみでStripe Checkout(先払い)かStripe Invoice(後払い)かを判定しているが、価格が確定している商品でも「注文後払い」を選べるようにしたい(例: 家電は後払い、ハイブランドは先払い)。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 商品ごとに支払いタイミングを設定する (Priority: P1)

運営者は、商品カタログの管理画面で商品ごとに「注文時に支払ってもらう」か「注文後に請求書で支払ってもらう」かを設定できる。これにより、商品カテゴリや取引慣行に応じた支払いポリシー(例: 家電は後払い、ハイブランド品は先払い)を柔軟に運用できる。

**Why this priority**: この設定機能がなければ、他のすべてのシナリオが成立しない。本機能の土台。

**Independent Test**: 商品管理画面で任意の商品の支払いタイミングを「注文後払い」に変更し、保存できることを確認するだけで独立して価値を検証できる。

**Acceptance Scenarios**:

1. **Given** 価格が確定している商品を編集している、**When** 支払いタイミングを「注文後払い」に設定する、**Then** 設定が保存され、以後この商品はカートに入ると注文後払いの対象になる
2. **Given** 価格が未確定(個別見積もり)の商品を編集している、**When** 支払いタイミングを「注文時払い」に変更しようとする、**Then** 価格未確定の商品は注文後払いに固定されている旨が示され、変更できない
3. **Given** 商品を「価格未確定(個別見積もり)」として設定している、**When** 商品編集画面を表示する、**Then** ランク別価格の入力欄は表示されない(入力しても実際の購入時には使われないため、混乱を避けるために非表示にする)

---

### User Story 2 - 支払いタイミングが混在するカートをチェックアウトする (Priority: P1)

会員は、支払いタイミングの異なる商品(例: 先払いのハイブランド品と後払いの家電)を同じカートに入れて、1回のチェックアウト操作で購入手続きを完了できる。システムが裏側で自動的に支払い方法ごとに注文を振り分けるため、会員自身がカートを分ける必要はない。

**Why this priority**: 本機能の主目的であり、会員が実際に体験する価値そのもの。

**Independent Test**: 先払い商品と後払い商品を1つずつカートに入れてチェックアウトし、先払い分はその場でのオンライン決済へ、後払い分は請求書発行待ちの状態へ、それぞれ問題なく進められることを確認する。

**Acceptance Scenarios**:

1. **Given** カートに注文時払いの商品のみが入っている、**When** チェックアウトする、**Then** 従来通り1件の注文が作成され、オンライン決済に進む
2. **Given** カートに注文後払いの商品のみが入っている(価格未確定商品を含む場合も含む)、**When** チェックアウトする、**Then** 従来通り1件の注文が作成され、請求書発行待ちの状態になる
3. **Given** カートに注文時払いの商品と注文後払いの商品が両方入っている、**When** チェックアウトする、**Then** 2件の注文が作成され、注文時払い分はオンライン決済へ、注文後払い分は請求書発行待ちの状態へ、それぞれ進む
4. **Given** 上記3の状況でオンライン決済分の支払いが完了した、**When** 完了画面を確認する、**Then** 会員はもう一方の注文(請求書発行待ち)の存在と状態も合わせて確認できる

---

### User Story 3 - カート画面で支払いタイミングごとに商品をグループ表示する (Priority: P1)

会員は、カート画面(カートサイドバー・チェックアウト画面)を開いた時点で、商品が「注文時に支払う商品」と「注文後に請求される商品」に明確にグループ分けされて表示されるため、チェックアウトを実行する前に、どの商品がいつ支払われるのかを把握できる。決済完了後になって初めて分割の事実を知ることがないようにする。

**Why this priority**: チェックアウト完了後に分割の事実を知る設計だけでは、会員が「思っていたのと違う」と驚く可能性がある。事前の透明性はUser Story 2で実現する分割機能が信頼して使われるための前提条件であり、同等の優先度とする。

**Independent Test**: 支払いタイミングの異なる商品をカートに追加し、チェックアウトを実行せずカート画面を開くだけで、2つのグループに分かれて表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** カートに注文時払い商品と注文後払い商品が両方入っている、**When** カート画面を表示する、**Then** 商品が「注文時に支払う商品」グループと「注文後に請求される商品」グループに分かれて表示される
2. **Given** カートに単一の支払いタイミングの商品のみが入っている、**When** カート画面を表示する、**Then** グループ分けの表示は行われない(従来通りの見た目のまま)
3. **Given** カート画面でグループ分けが表示されている、**When** 各グループを確認する、**Then** グループごとの小計金額が表示される

---

### User Story 4 - 分割された注文をひとつの取引として把握する (Priority: P2)

運営者は、チェックアウト分割によって生成された2件の注文が、同一の会計(1回のチェックアウト操作)に由来することを、注文管理画面上で判別できる。会員も自身の注文履歴で同様に把握できる。

**Why this priority**: 分割自体はUser Story 2で実現されるが、運営者・会員が「なぜ注文が2件に増えたのか」を理解できないと問い合わせ対応コストが増える。運用上重要だが、分割そのものより優先度は一段低い。

**Independent Test**: 分割チェックアウトを1回実行し、生成された2件の注文が注文一覧・注文詳細のいずれからも「同一のチェックアウトに由来する」と表示されることを確認する。

**Acceptance Scenarios**:

1. **Given** 1回のチェックアウトから2件の注文が分割生成された、**When** 運営者が注文管理画面でどちらか一方の注文を開く、**Then** もう一方の関連注文への参照が表示される
2. **Given** 分割されていない通常の注文(1件のみ)、**When** 運営者が注文詳細を開く、**Then** 関連注文の表示は行われない

---

### User Story 5 - 月間購入上限を超えるチェックアウトを防ぐ (Priority: P2)

会員の月間購入上限は、チェックアウトが分割されるかどうかに関わらず、カート全体の合計金額(価格が確定している商品の合計)に対して一度だけ判定される。上限を超える場合、分割後の一方だけが先に進むことはなく、チェックアウト全体がブロックされる。

**Why this priority**: 既存の月間購入上限機能の一貫性を保つための安全策。分割機能がなくても上限チェック自体は既に存在するため、本機能特有の追加要件としては優先度中程度。

**Independent Test**: 月間購入上限を超える金額になるよう、注文時払い商品と注文後払い商品を組み合わせてカートに入れてチェックアウトを試み、両方の注文が作成されずにブロックされることを確認する。

**Acceptance Scenarios**:

1. **Given** カート内の価格確定商品の合計が会員の月間購入上限を超えている、**When** チェックアウトする(注文時払い・注文後払いが混在していても)、**Then** 注文は1件も作成されず、上限超過である旨が案内される
2. **Given** カート内の価格確定商品の合計は上限内だが、価格未確定商品も含まれている、**When** チェックアウトする、**Then** 価格確定分のみで上限判定が行われチェックアウトは進む(価格未確定分の上限判定は、従来通り運営者が金額確定する際に別途行われる)

---

### Edge Cases

- カートが単一の支払いタイミングの商品のみで構成されている場合、注文は分割されず1件のみ作成される(既存動作を維持)
- 価格未確定(個別見積もり)の商品は、支払いタイミング設定に関わらず常に注文後払いグループに含まれる
- 注文後払いグループの中に価格確定商品と価格未確定商品が混在する場合でも、運営者による内容確認・請求書発行のプロセスは従来通り1回で完結する(価格確定商品分について追加の入力は不要)
- 分割によって生成された2件の注文のうち、注文時払い分の決済がキャンセルされた場合と、注文後払い分だけが先に処理される場合の状態管理は、それぞれの注文が独立したライフサイクルとして扱われる
- カート内が単一の支払いタイミングのみの場合、カート画面のグループ表示は行わない(視覚的ノイズを避け、従来通りの見た目を維持する)
- 注文の分割処理中に、2件の注文のうち一方の記録保存が技術的な理由(システム障害等)で失敗した場合、既に保存が成功していたもう一方の記録も取り消され、注文自体が成立しなかった状態に戻す

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 運営者は商品ごとに支払いタイミング(「注文時に支払う」/「注文後に請求する」)を設定できなければならない
- **FR-002**: 価格が確定していない(個別見積もりが必要な)商品は、支払いタイミングが常に「注文後に請求する」に固定され、運営者が「注文時に支払う」へ変更することはできない
- **FR-003**: 会員のカートが単一の支払いタイミングの商品のみで構成される場合、システムは従来通り1件の注文を作成しなければならない
- **FR-004**: 会員のカートに支払いタイミングの異なる商品が混在する場合、システムはチェックアウト時に自動的に注文を2件(「注文時払い」グループと「注文後払い」グループ)に分割しなければならない
- **FR-005**: 「注文時払い」グループの注文は、既存のオンライン決済フローで処理されなければならない
- **FR-006**: 「注文後払い」グループの注文(価格未確定商品を含む)は、既存の請求書発行フローで処理されなければならない
- **FR-007**: 分割によって生成された2件の注文は、同一のチェックアウトに由来することが運営者・会員の双方から判別できる形で関連付けられなければならない
- **FR-008**: 会員の月間購入上限チェックは、分割前のカート合計金額(価格が確定している商品のみの合計)に対して一度だけ行われなければならない
- **FR-009**: 月間購入上限を超える場合、分割後のいずれの注文も作成されてはならない(一方のみの作成は許可されない)
- **FR-010**: 「注文後払い」の注文に含まれる価格確定商品についても、請求書の送付前に運営者が内容を確認するプロセスを経なければならない(自動送信は行わない)
- **FR-011**: 価格未確定商品の金額確定プロセス(運営者による個別見積もり入力と、それに伴う月間購入上限の再判定)は、既存の仕組みを変更してはならない
- **FR-012**: 商品が「価格未確定(個別見積もり)」に設定されている場合、商品編集画面はランク別価格の入力欄を表示してはならない(入力しても購入時には使用されず、運営者を混乱させるため)
- **FR-013**: カート画面(カートサイドバー・チェックアウト画面)は、支払いタイミングの異なる商品が混在する場合、商品を「注文時払い」グループと「注文後払い」グループに分けて表示しなければならない
- **FR-014**: FR-013のグループ表示では、各グループの小計金額が表示されなければならない
- **FR-015**: カート内が単一の支払いタイミングのみで構成される場合、カート画面はグループ表示を行ってはならない(従来通りの表示のまま)
- **FR-016**: チェックアウト分割によって生成される2件の注文の記録保存は、両方とも成功するか、両方とも成立しない(記録が残らない)かのいずれかでなければならない。一方のみが記録され、もう一方が失われる状態を許してはならない
- **FR-017**: チェックアウトを「注文時払い」/「注文後払い」に振り分ける判定は、会員が閲覧・操作できる情報(カート画面の表示データ等)を根拠にしてはならず、常にシステムが管理する商品情報(改変不可能な情報源)に基づいて行われなければならない

### Key Entities

- **商品(Product)**: 支払いタイミング属性(「注文時払い」/「注文後払い」)を持つ。価格が未確定な商品は支払いタイミングが「注文後払い」に固定される
- **注文(Order)**: 決済方法(オンライン決済/請求書)を持つ。チェックアウト分割によって生成された注文は、同一チェックアウトに由来する他の注文との関連付け情報を持つ

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 運営者は既存の商品編集画面の操作の延長で、追加の説明を受けずに支払いタイミングを設定できる
- **SC-002**: 支払いタイミングが混在するカートを持つ会員は、1回のチェックアウト操作だけで、オンライン決済への案内と請求書発行待ちの案内の両方に到達できる
- **SC-003**: 分割によって生成された注文は、運営者・会員のいずれの画面からも100%の精度で「同一チェックアウト由来」と判別できる
- **SC-004**: 月間購入上限を超えるチェックアウトは、分割の有無によらず常に0件の注文作成でブロックされる
- **SC-005**: 支払いタイミングが混在するカートを持つ会員は、チェックアウトを実行する前にカート画面を見るだけで、どの商品が今支払われ、どの商品が後で請求されるかを100%判別できる

## Assumptions

- 「価格未確定商品は請求書払い」という既存の運用ルールは変更せず、新たに追加されるのは「価格確定済み商品でも請求書払いを選べる」という選択肢である
- 1つのカート内の支払いタイミングは「注文時払い」「注文後払い」の2区分のみを想定し、3区分以上への拡張は本機能のスコープ外である
- 分割後の請求書払い注文における金額確定・請求書発行フローは、運営者による手動確認を経る現行プロセスをそのまま踏襲する
- 本機能は既存の関連する取り組み(003-checkout-invoice-e2e)の完了後に実装に着手する前提であり、本specの作成時点ではドキュメント化のみを目的とする
