# Quickstart: 法人会員（B2B）対応の検証手順

実装完了後、以下のシナリオを手動（またはE2E）で確認し、各User Storyが独立して動作することを検証する。

## 前提

```bash
supabase start
pnpm dev
```

Clerk開発環境でOrganizations機能が有効になっていること（Clerk Dashboard > Organizations > Enable）。

## シナリオ1: 代表者のセルフサインアップ（User Story 1）

1. `/sign-up` で「法人として登録」を選び、会社名・代表者名・本店所在地・電話番号・適格請求書発行事業者登録番号を入力してサインアップを完了する
2. 適格請求書発行事業者登録番号に不正な形式（例: 数字13桁のみで"T"なし）を入力し、登録がブロックされることを確認する
3. 正しい形式で再登録し、オンボーディングでランクを選択する
4. **期待結果**: `organizations` テーブルに新規レコードが作成され、`organization_memberships` に自分が `org:admin` として登録されている
5. そのまま1人で発注し、月次上限内であれば通常のCheckout/Invoiceフローに進むことを確認する（承認待ちにならない）

## シナリオ2: 個人会員・法人代表者のプロフィール必須化（User Story 2）

> PR #143の設計変更により、既存会員への遡及対応（旧シナリオ2の3〜4、FR-020）は本番未リリースのためスコープ外。以下は新規サインアップ時のみを検証する。

1. 新規に個人会員としてサインアップし、`/onboarding/plan` で氏名・電話番号を未入力のままオンボーディングを完了しようとする
2. **期待結果**: 入力が必須項目としてブロックされる。電話番号に不正な形式（例: 5桁の数字）を入力した場合もブロックされる
3. シナリオ1の法人代表者の`users`レコードを確認し、`/onboarding/organization`で入力した代表者の姓・名・電話番号がそのまま`first_name`/`last_name`/`phone_number`に反映されていることを確認する（別画面での再入力が発生しないこと）

## シナリオ3: メンバー招待（User Story 3）

1. シナリオ1の代表者アカウントで `/org/members` から別のメールアドレスを招待する
2. 招待メール（またはClerk Dashboardの招待リンク）から招待を承諾する
3. **期待結果**: `organization_memberships` に `org:member` として新しいレコードが追加され、メンバー一覧に表示される
4. 既に個人会員として登録済みのメールアドレスを招待してみる
5. **期待結果**: 招待の承諾がブロックされる（FR-023、個人会員と法人組織メンバーは排他的）

## シナリオ4: 発注承認フロー（User Story 4）

1. シナリオ3の一般担当者アカウントでログインし、発注する
2. **期待結果**: 注文が `pending_approval` になり、Stripe Checkout SessionまたはInvoiceが作成されていないことを確認する（Stripeダッシュボード側でも未作成であることを確認）
3. 代表者(org:admin)アカウントで `/org/orders/pending` から承認する
4. **期待結果**: 注文が既存のCheckout/Invoiceフローに進む
5. 別の注文を却下し、`cancelled` になることを確認する

## シナリオ5: 組織の共有住所帳（User Story 5）

1. 一般担当者が組織の住所帳に新しい納品先を登録する
2. 代表者が発注時にその住所を選択肢として見られることを確認する
3. 個人会員（組織なし）でログインし、組織の住所帳という概念自体が表示されないことを確認する

## シナリオ5.5: ランク参照の一元化確認（FR-024, R11）

1. 組織のランクを個人会員の`users.rank`の既定値とは異なるランクに設定する（例: 組織側は`advanced`、当該ユーザーの`users.rank`は未使用のまま既定値）
2. 組織のメンバーとしてログインし、`/shop`で商品カタログを閲覧する
3. **期待結果**: 組織のランク（`advanced`）に基づいた閲覧可否になっており、`users.rank`の既定値に基づいた閲覧可否になっていないことを確認する

## シナリオ6: 月次上限の合算（FR-004, FR-016）

1. org:memberが上限の80%相当を発注（承認待ちのまま放置）
2. org:adminが上限の80%相当を発注しようとする
3. **期待結果**: 承認待ちの金額もすでに合算されているため、上限超過エラーになる
4. 最初の承認待ち注文を却下する
5. **期待結果**: 却下により合算対象から外れ、再度org:adminが同額を発注できるようになる

## シナリオ7: 唯一の管理者の退会（FR-017）

1. メンバーが自分1人だけの組織で、org:adminが退会を試みる → 退会でき、組織もクローズされることを確認する
2. メンバーが2人以上いる組織で、唯一のorg:adminが退会を試みる → ブロックされ、「先に他のメンバーを管理者に昇格させてください」という案内が出ることを確認する

## シナリオ8: 個人会員フローの非破壊（FR-013）

1. 組織を作らず個人会員としてサインアップし（プロフィール入力を除く）、既存の発注〜住所管理〜決済の一連の操作が本機能追加前と変わらず動作することを確認する
