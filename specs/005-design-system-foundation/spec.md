# Feature Specification: デザインシステム基盤の導入

**Feature Branch**: `feature/design-system-foundation`

**Created**: 2026-08-08

**Status**: Draft

**Input**: User description: "デザインシステム導入: Tailwind v4によるデザイントークン設計、Storybookによるプリミティブコンポーネント開発基盤の構築。既存画面（ECサイトフロントエンド）はまだ仮実装段階であり、今回のスコープはトークン設計とプリミティブコンポーネント（ボタン、フォーム部品など）+ Storybook基盤の導入までとし、既存画面への適用は別のユーザーストーリーとして切り離す。目的は商用サービスとして長期的にUI/UXを継続改善していくための基盤づくりであり、E2Eテスト（Playwright、getByRole/name属性ベース）への影響を最小化しつつ進める。"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - デザイントークンの一元管理 (Priority: P1)

デザイン担当者・開発者が、色・余白・タイポグラフィ等の見た目に関する値を、画面ごとに個別のスタイルとして書くのではなく、単一のトークン定義を参照するだけで統一された見た目を実現できる。

**Why this priority**: トークンはプリミティブコンポーネント・Storybook双方の土台であり、これがないと他の2つのユーザーストーリーが成立しない。単体でも「新しいUI要素を作るときに毎回配色を決め直さなくてよい」という価値を既存画面に対しても提供できる。

**Independent Test**: 既存画面のいずれか1箇所（例: ボタンの背景色）をトークン参照に置き換え、見た目が変わらないこと、かつトークンの値を1箇所変更するとその画面にも反映されることを確認すれば独立して価値を検証できる。

**Acceptance Scenarios**（受け入れ条件）

_開発者が確認できること_

1. **Given** 色・余白・タイポグラフィのトークンが定義されている、**When** 新しいUI要素を実装する、**Then** 個別に値を決め打ちせずトークン参照だけで既存画面と統一感のある見た目にできる
2. **Given** あるトークンの値（例: プライマリカラー）を1箇所変更する、**When** トークンを参照している既存コンポーネント・画面を確認する、**Then** 変更がすべての参照箇所に反映される

_システムが保証すること_

1. トークンの定義箇所は一意であり、同じ意味の値（例: プライマリカラー）が複数箇所にハードコードされることはない
2. トークン定義の変更は、既存のE2Eテスト（Playwright）が参照するrole・name・要素構造に影響を与えない

---

### User Story 2 - プリミティブコンポーネントの実装 (Priority: P2)

開発者が、ボタン・入力欄・チェックボックス等の基本的なUI部品を、画面ごとに個別実装するのではなく、共通のプリミティブコンポーネントとして再利用できる。

**Why this priority**: トークン（User Story 1）を前提として、実際に再利用可能な形に落とし込む工程。これが揃うことで初めて画面実装の際に一貫したUIを組み立てられるようになる。

**Independent Test**: ボタン・テキスト入力・チェックボックスのいずれか1種類のプリミティブコンポーネントを実装し、それを使って簡単なフォームを組み立てて意図した見た目・状態（通常・ホバー・disabled等）になることを確認すれば独立して価値を検証できる。

**Acceptance Scenarios**（受け入れ条件）

_開発者が確認できること_

1. **Given** プリミティブコンポーネント（ボタン・入力欄・チェックボックス等）が実装されている、**When** それらを組み合わせて画面を組み立てる、**Then** 個別にスタイルを書かずに一貫した見た目のUIを組み立てられる
2. **Given** プリミティブコンポーネントには複数の状態（通常・ホバー・フォーカス・disabled・エラー等）がある、**When** 各状態を確認する、**Then** すべての状態が意図したとおりに表示される

_システムが保証すること_

1. プリミティブコンポーネントは内部でUser Story 1のトークンのみを参照し、独自の色・余白の値をハードコードしない
2. プリミティブコンポーネントは意味的に適切なHTML要素・ARIA role（例: ボタンは`<button>`またはrole="button"）でレンダリングされ、既存のE2Eテストが使用する`getByRole`ベースのセレクタと衝突しない

---

### User Story 3 - Storybookによる開発・確認基盤 (Priority: P3)

開発者が、Clerk認証・カート状態・決済フローといった実際の業務フローを経由せずに、個々のプリミティブコンポーネントの見た目・状態をブラウザ上で単体確認・反復開発できる。

**Why this priority**: User Story 1・2で作られたトークン・コンポーネントが存在して初めて確認基盤として意味を持つため、優先度は最も低いが、商用サービスとして継続的にUI/UXを改善し続けるための土台として導入する。

**Independent Test**: プリミティブコンポーネントを1つ選び、それに対応するStorybookのstoryファイルを作成し、`pnpm storybook`（相当のコマンド）でブラウザから直接その部品の全状態を確認できることを確認すれば独立して価値を検証できる。

**Acceptance Scenarios**（受け入れ条件）

_開発者が確認できること_

1. **Given** プリミティブコンポーネントにstoryが作成されている、**When** 開発者がStorybookを起動する、**Then** ログイン・オンボーディング等の業務フローを一切経由せずに、そのコンポーネントの各状態（通常・ホバー・disabled・エラー等）を一覧で確認できる
2. **Given** Storybook上でコンポーネントのコードを変更する、**When** 変更を保存する、**Then** アプリ全体を再ビルドすることなく変更が画面に反映される

_システムが保証すること_

1. Storybookの導入・story追加は、既存のNext.jsアプリのビルド・E2Eテスト実行に影響を与えない（Storybook用の設定・依存はアプリ本体のビルド対象から分離されている）

---

### Edge Cases

- トークンが定義されていない値（未定義の色・余白）を参照しようとした場合、開発時にビルドエラー等で検知できるか、それとも黙って無効な値になるか
- プリミティブコンポーネントに、まだトークン化されていない例外的なスタイル要求（特定画面だけの特殊な見た目）が発生した場合、どう扱うか
- Storybookの起動に必要な環境（Clerk・Supabase等の外部サービスの認証情報）が無い開発環境でも、コンポーネント確認自体は行えるか

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: システムは色・余白・タイポグラフィ（フォントサイズ・行間・フォントウェイト等）のデザイントークンを、コード上の単一の定義箇所として提供しなければならない
- **FR-002**: システムは、少なくともボタン・テキスト入力・チェックボックス・ラジオボタン・セレクトの5種類のプリミティブコンポーネントを提供しなければならない
- **FR-003**: 各プリミティブコンポーネントは、通常・ホバー・フォーカス・disabled・エラー（該当するもののみ）の状態表示に対応しなければならない
- **FR-004**: 各プリミティブコンポーネントは、意味的に適切なHTML要素またはARIA roleでレンダリングされなければならない
- **FR-005**: システムは、Storybook等のツールを用いて、業務フロー（認証・カート・決済）を経由せずに各プリミティブコンポーネントを単体表示・確認できる手段を提供しなければならない
- **FR-006**: プリミティブコンポーネント・Storybookの追加は、既存の単体テスト・統合テスト・E2Eテスト（`pnpm test` / `pnpm test:e2e`）の実行結果に影響を与えてはならない
- **FR-007**: 本機能のスコープは、トークン定義・プリミティブコンポーネント・Storybook基盤の導入までとし、既存画面（`(member)`配下等）へのコンポーネント適用・置き換えは含まない

### Key Entities

- **デザイントークン**: 色・余白・タイポグラフィ等、UIの見た目を構成する最小単位の値。コード上に一意に定義され、コンポーネント・画面から参照される
- **プリミティブコンポーネント**: デザイントークンを参照して実装される、再利用可能な最小単位のUI部品（ボタン・入力欄等）。特定の画面・業務ロジックに依存しない
- **Story**: Storybook上で、あるプリミティブコンポーネントの特定の状態・組み合わせを表示するための定義

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 開発者が、業務フロー（ログイン・オンボーディング等）を経由せず、起動から10秒以内に任意のプリミティブコンポーネントの全状態を確認できる
- **SC-002**: 新規のプリミティブコンポーネントを1つ追加する際、色・余白の値を直接指定する記述が0件で実装できる（すべてトークン参照）
- **SC-003**: 本機能の導入前後で、既存のPlaywright E2Eテストの成功率に変化がない（100%互換）
- **SC-004**: 提供されたプリミティブコンポーネントの種類数（5種類以上）と、それぞれの対応状態数（4種類以上）を満たしている

## Assumptions

- 対象範囲は、会員向け画面・管理画面を問わず今後実装するすべてのUIで共通利用することを前提とするが、本フィーチャー自体では既存画面への適用は行わない
- レスポンシブ対応（モバイル・デスクトップ双方の表示）は、トークン・プリミティブコンポーネントの設計段階で考慮するが、既存画面側の対応状況の変更は本フィーチャーのスコープ外とする
- ダークモードは本フィーチャーのスコープ外とし、必要になった時点で別フィーチャーとして追加する
- Storybookの実行・閲覧は開発者のローカル環境を前提とし、社外向けの公開・デプロイは本フィーチャーのスコープ外とする
